# Track B — Platform access (iOS / macOS / Android / Google Photos / DTI / DMA)

Research date: 2026-11-03 (repaired 2026-11-03 after audit; see "Audit log" at the end). All source dates are the date of the cited document, not today's date.
Tagging: exactly `[sourced: url, date]`, `[estimated: method with inputs]`, or `[unknown]` — per README. Where a source is a press article or a community post rather than a vendor/regulator document, that is stated inside the `[sourced: …]` tag; no fourth tag is used.

## 1. Questions asked

1. Can a third-party iOS app read the user's full Photos library via PhotoKit (originals, metadata, faces, iCloud-only originals)? What does `isNetworkAccessAllowed` do? Limited Library mode? Rate/battery limits?
2. Can an iOS app upload a large (the brief's illustrative figure: 100 GB) library in the background? What do BGProcessingTask / background URLSession allow, and what do Ente, Immich, Google Photos, Dropbox actually do?
3. Can a Mac app read `Photos Library.photoslibrary` directly (osxphotos), including originals and faces/people? Is that the realistic migration path, and what does a 100k-photo export look like?
4. Google Photos API after March 31 2025: what was removed, what the Picker API allows, Takeout mechanics, "Transfer your data" to iCloud.
5. Apple "Transfer a copy of your data": Apple→Google (2021) and Google→iCloud (2024): formats, what is lost, eligibility.
6. Data Transfer Initiative (DTI) in 2026: members, third-party destinations, is DTP maintained, can a startup become a destination?
7. EU DMA Art. 6(9) continuous real-time portability: what Apple and Google shipped, developer APIs, enforcement, does it give a startup a lever to read a Photos library continuously?
8. Android: MediaStore full access, scoped storage, background upload constraints, is it materially easier than iOS?

Seed assumptions tested: A1 (Google removed third-party read access March 2025, durable), A2 (full-library export to a third party is feasible on iOS).

## 2. Findings per question

### Q1. Apple PhotoKit: full library read

**Full-library enumeration and originals.** With `.readWrite` or `.readOnly` authorization at status `.authorized`, PhotoKit exposes every `PHAsset`; `PHAssetResourceManager` returns original resource bytes. The Background Resource Upload article (Q2) confirms Apple expects third-party backup apps to hold "full library access" and iterate the whole library ("Return this value during initial library uploads when you have remaining assets to process") [sourced: https://developer.apple.com/documentation/photokit/uploading-asset-resources-in-the-background, Apple doc, fetched 2026-11-03].

**iCloud-only originals.** `PHImageRequestOptions.isNetworkAccessAllowed`: "If `true`, and the requested image is not stored on the local device, Photos downloads the image from iCloud... If `false` (the default), and the image is not on the local device, the `PHImageResultIsInCloudKey` value in the result handler's `info` dictionary indicates that the image is not available unless you enable network access." Available iOS 8.0+ [sourced: https://developer.apple.com/documentation/photos/phimagerequestoptions/isnetworkaccessallowed, fetched 2026-11-03]. The same semantics apply to `PHAssetResourceRequestOptions.isNetworkAccessAllowed` (iOS 9.0+): if false and data is not local, "Photos calls the completionHandler... with an NSError object indicating that the resource requires network access" [sourced: https://developer.apple.com/documentation/photos/phassetresourcerequestoptions/isnetworkaccessallowed, fetched 2026-11-03]. So `requestImageDataAndOrientation` on an iCloud-only asset does a network fetch only when the flag is set; it is a per-request foreground download, with no documented throughput guarantee. Ente's docs corroborate the practical cost: "On iPhone, Ente may first download the full-resolution original from iCloud." and "for backup, Ente always retrieves the original, full-resolution photo or video directly from iCloud." and "Keep the device connected to the internet while that backup finishes." [sourced: https://ente.com/help/photos/faq/backup-and-sync, fetched 2026-11-03]. A developer-forum report of `requestImageDataAndOrientation` callbacks never firing for iCloud assets exists but is a single anecdote [sourced: https://developer.apple.com/forums/thread/813350, community post, not an Apple statement].

**Faces / People: not exposed to third parties (no public API found; the evidence is community-sourced, not an Apple statement).** Apple Developer Forums thread "Access face tags" (question Dec 2019; answers June 2020 by community posters "Jordan" and "bwebster", no Apple-staff marking): "No, there is not an API to access people data in PhotoKit as of now." and "There's no public API to do this, and Apple actually goes to specific lengths to prevent accessing face/person information using PhotoKit. Even using private APIs, access to that info is denied to third party apps" [sourced: https://developer.apple.com/forums/thread/126711, Jun 2020, community answers]. No PhotoKit symbol for persons/faces appears in Apple's current Photos framework documentation (negative search of developer.apple.com/documentation/photos, 2026-11-03). Status: no evidence that face/people names are available to iOS third parties; the thread is six years old, so this is "very likely still true", not "verified" [unknown — no primary Apple statement either way].

**Limited Library.** `PHAuthorizationStatus.limited` (iOS 14.0+): "The user authorized this app for limited photo library access." Apps may present `presentLimitedLibraryPicker` and can set `PHPhotoLibraryPreventAutomaticLimitedAccessAlert` [sourced: https://developer.apple.com/documentation/photos/phauthorizationstatus/limited, fetched 2026-11-03]. A limited-access app sees only user-selected assets; the background upload extension explicitly requires `.authorized` (full) [sourced: Apple upload-extension article, above].

**Rate / battery limits.** Apple publishes no PhotoKit request rate limit, throttle, or battery budget; the only performance guidance in the framework docs is `PHCachingImageManager`, "optimized for batch preloading large numbers of assets": "a caching image manager can prepare asset images in the background in order to eliminate delays" [sourced: https://developer.apple.com/documentation/photos/phcachingimagemanager, fetched 2026-11-03] — this is about thumbnails, not originals. Numeric limit: [unknown — searched Apple docs for PHImageManager/PHCachingImageManager; no throttle documented]. Field evidence of practical limits is anecdotal: Immich issue #32747 (2026-10-27, iPhone 16 Pro, app v3.3.5): "I observed over 1,300 open connections on my phone at the same time" while originals were being pulled from iCloud; maintainer agg23 (2026-10-27): "The Immich app itself doesn't open any connections to iCloud" and the app is limited to three asset uploads at once — i.e., the iCloud fetch is done by the OS, outside the app's control [sourced: https://github.com/immich-app/immich/issues/32747, 2026-10-27]. Immich #32258 (2026-10-09, iPhone 12): "Phone gets heated up after few minutes" during sync — closed the same day as a user network-setup problem, not a PhotoKit limit [sourced: https://github.com/immich-app/immich/issues/32258, 2026-10-09]. Net: the binding constraints on a full-library read are (a) iCloud-original download, which the OS performs per request at an undocumented rate, and (b) device storage for the downloaded originals (Ente: "which can use extra device storage"), not a documented API quota.

### Q2. iOS background execution for a large (illustrative 100 GB) upload

The 100 GB figure is the brief's illustrative library size, not a measured value [estimated: assumption supplied by the brief; no source].

**Generic background APIs (pre-iOS 26.1 reality).**
- `BGProcessingTask` (iOS 13+): "Although processing tasks can run for minutes, the system can interrupt the process... Processing tasks run only when the device is idle. The system terminates any background processing tasks running when the user starts using the device." [sourced: https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask, fetched 2026-11-03]. No numeric budget is documented [unknown].
- Background `URLSession` ("Downloading files in the background", Apple): "These tasks continue to run even when your app is suspended"; "If the system terminated the app while it was suspended, the system relaunches the app in the background"; crucially, "When the system resumes or relaunches your app, it uses a rate limiter to prevent abuse of background downloads. When your app starts a new download task while in the background, the task doesn't begin until the delay expires. The delay increases each time the system resumes or relaunches your app." and "The delay is reset to 0 whenever the user brings your app to the foreground."; "In cases where the transfer is initiated while the app is in the background, the session configuration's `isDiscretionary` property is treated as being `true`"; "Only upload tasks from a file are supported (uploads from data instances or a stream fail after the app exits)." [sourced: https://developer.apple.com/documentation/foundation/downloading-files-in-the-background (read via the /tutorials/data JSON endpoint), fetched 2026-11-03]. `URLSessionConfiguration.background(withIdentifier:)`: "If the user terminates the app from the multitasking screen, the system cancels all of the session's background transfers. In addition, the system does not automatically relaunch apps that were force quit by the user."; "When transferring large amounts of data, you are encouraged to set the value of [`isDiscretionary`] to `true`." iOS 8.0+ [sourced: https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:), fetched 2026-11-03]. Implication for a multi-GB staged upload: each asset must first be written to a file (doubling local storage transiently), the app must be woken to enqueue more work, each wake incurs an escalating system delay, and a force-quit cancels everything. Apple publishes no cap on the number of queued tasks [unknown].

**What the apps say.**
- Ente (official docs, verbatim): "Background sync isn't currently consistent on iOS and on certain Android devices."; mechanism is silent notifications ("Ente asks iOS to start a short backup from time to time"; "iOS briefly wakes Ente to upload new photos"); "Videos may not upload in background due to size limitations"; "Do not swipe Ente away from the app switcher." / "iOS cannot wake Ente for background backups after the app has been closed this way."; "For large initial backups and videos, use Backup mode and keep Ente open on screen." / "Switching apps pauses Backup mode" [sourced: https://ente.com/help/photos/faq/backup-and-sync, fetched 2026-11-03]. Ente's co-founder on Hacker News (vishnumohandas, 2023-07-11): "Currently on iOS, our servers send silent pushes to your device every hour." "This wakes up the app and gives us 30 seconds to execute a background sync" "This is not sufficient to backup videos, but it works pretty well for incremental backup of photos" [sourced: https://news.ycombinator.com/item?id=36674348, 2023-07-11, developer comment on a community forum].
- Immich: issue #20227 (opened 2025-07-25, server/app v1.136.0): "the new photos will not sync to Immich unless I open the app even once"; maintainer alextran1502 2025-07-25: "Correct, this part hasn't been implemented yet"; 2025-08-17: "For the beta timeline, background queuing is not yet working"; 2025-09-02: "Implemented in 1.140.0" [sourced: https://github.com/immich-app/immich/issues/20227]. Discussion #25897 (2026-02-04, iOS 26.3.2, Immich 2.5.3, iPhone 16 Pro Max): "when i start backup and move to other app , the backup stops"; a collaborator points to the FAQ; user githubkusi (2026-02-08) adds that Apple's new extension makes this "Technically... possible since iOS 26.1, but it seems not straight forward to implement" [sourced: https://github.com/immich-app/immich/discussions/25897, 2026-02-04/08]. The FAQ states foreground and background backup "don't communicate or interact with each other" and that on iOS the OS decides "when the background task can run and how long it can run", based on factors "most of which the Immich app has no control over" [sourced: https://docs.immich.app/FAQ, fetched 2026-11-03].
- Google Photos iOS help: "Keep the Photos app open and your phone plugged in for best results"; "Standby mode" keeps backup going while the phone is not in use; "To turn off Standby Mode, close the Google Photos app" [sourced: https://support.google.com/photos/answer/6193313?co=GENIE.Platform%3DiOS, fetched 2026-11-03].
- Dropbox (fetched this round): "iOS limits background apps to extend battery life."; "Be sure Background app refresh is enabled."; "Avoid the Low Power Mode setting." (page updated 2025-02-14) [sourced: https://help.dropbox.com/create-upload/upload-not-working-in-background, 2025-02-14]. "Overnight uploads allows you to upload your photos and videos continuously through the night, keeping the Dropbox mobile app open and dimming your device's brightness." "This feature is available on iOS devices only." Requirements: "Keep your Dropbox app open." / "Make sure your phone is connected to Wi-Fi." / "Keep your phone plugged into a charger" (page updated 2026-09-17) [sourced: https://help.dropbox.com/create-upload/camera-uploads-overview, 2026-09-17]. So even Google and Dropbox do NOT fully get around it; both instruct users to keep the app open — and Dropbox's page, updated 2026-09-17 (eleven months after iOS 26.1), still documents the keep-the-app-open path.

**The material change: iOS 26.1 Background Resource Upload extension.**
- "PhotoKit's Background Resource Upload extension enables apps to deliver seamless cloud backup experiences. The system manages uploads on your app's behalf, processing them in the background even when people switch to other apps or lock their devices." Available via `PHBackgroundResourceUploadExtension` on iOS 26.1 (deprecated in iOS 27.0: "Adopt PHBackgroundResourceUploadJobExtension instead") and `PHBackgroundResourceUploadJobExtension` on iOS 27.0 / macOS 27.0 / Catalyst 27.0 [sourced: https://developer.apple.com/documentation/photokit/uploading-asset-resources-in-the-background, fetched 2026-11-03; availability metadata on https://developer.apple.com/documentation/photos/phbackgroundresourceuploadextension and .../phbackgroundresourceuploadjobextension].
- Requirements: "Your app must have full library access before enabling the extension"; extension point `com.apple.photos.background-upload`; a hardcoded Info.plist key `BackgroundUploadURLBase` ("The system requires this key for network access validation"); `setUploadJobExtensionEnabled(_:)` on the host app [sourced: same article; https://developer.apple.com/documentation/photos/phphotolibrary/setuploadjobextensionenabled(_:)].
- Mechanics: one `PHAssetResourceUploadJob` per `PHAssetResource`; "The system enforces an inflight job limit." `jobLimit` is "The maximum number of unacknowledged upload jobs allowed." — numeric value not published [sourced: https://developer.apple.com/documentation/photos/phassetresourceuploadjob/joblimit; value [unknown]]. "The system automatically downloads asset resources before processing" (i.e., it fetches iCloud-only originals itself) and offers download-only jobs. Supports the IETF draft Resumable Uploads for HTTP (server must answer `OPTIONS` with `Upload-Limit` and send `104 (Upload Resumption Supported)`). "In production, the system applies the standard runtime limit on the extension" — the limit's value is not published [unknown]. Change tracking via `fetchPersistentChanges(since:)` [sourced: same article].
- Consent: press coverage says Apple "will require express user consent" for the extension [sourced: https://9to5mac.com/2025/10/24/ios-26-1-third-party-photos-backup-background/, 2025-10-24, press article]. The article says nothing about data-handling disclosure requirements; the earlier version of this file's claim to that effect is withdrawn.
- Adoption, Immich: discussion #23245 (2025-10-25) closed; maintainer bo0tzz: "This isn't really something to track as a feature request, nor is it something we're likely to add anytime soon." Contributor johannesvogel (2025-12-27) listed two blockers: "Apple forces developers to hardcode the URL that the photos will be uploaded to" and "the body of the HTTP request can only contain the asset data itself" (no multipart form fields). FawenYo (2026-01-13) offered a workaround ("BackgroundUploadURLBase doesn't strictly need to match the actual Immich server endpoint", "a temp solution") and (2026-01-30) announced a separate third-party app, YAIIU, built on the iOS 26.1 SDK that "will continuously upload your photos/videos to the Immich server". Later comments (2026-02-13, 2026-06-22 "on the eve of iOS 27", 2026-06-25, 2026-07-14) show no official Immich implementation [sourced: https://github.com/immich-app/immich/discussions/23245, 2025-10-25 to 2026-07-14].
- Adoption, Ente: issue #7127 (opened 2025-09-10, "Background synchronization does not work on iOS", still open): maintainer mnvr (2025-10-27) quoted Apple's extension announcement; (2025-11-17) adopting it "requires us to adopt a very different architecture than the current encrypt + upload pipeline" — "We will eventually do it, but it's not a trivial change." and "Background uploads should be working on iOS" via the existing path; contributor swiffer (2026-08-24) still calls the Apple API "the most reliable way" but "quite time consuming" [sourced: https://github.com/ente-io/ente/issues/7127, 2025-09-10 to 2026-08-24]. Ente PR #9810 "[mob][photos] Add iOS upload grace window and bg handoff" (2026-03-26) used a BGProcessing continuation, not the extension, and was auto-closed as stale 2026-05-06 [sourced: https://github.com/ente-io/ente/pull/9810]. So as of 2026-08-24 Ente had not shipped the extension.
- Adoption, Google Photos / Dropbox / OneDrive: no release note or help-page statement found that any of them has shipped the extension [unknown — web-search budget exhausted this round after the Dropbox help pages, which (2026-09-17) still describe Overnight uploads with the app open]. Only the independent YAIIU app above is a known shipping adopter.

Net: before iOS 26.1 a multi-GB background upload was not reliably possible on iOS — background URLSession rate-limits relaunches and requires file-staged uploads, BGProcessingTask runs only when idle, and every shipping app tells users to keep the app open. From iOS 26.1 (and more robustly iOS 27) Apple provides a system-managed, resumable, iCloud-aware background upload path specifically for full-library backup apps — but with an unpublished runtime limit and inflight job limit, a fixed destination base URL, raw-body uploads only, express user consent, and, a year after release, no major backup app (Immich, Ente, Google Photos, Dropbox) found to have shipped it.

### Q3. macOS direct library read (osxphotos)

- osxphotos reads "the Photos library database" (Photos.sqlite inside the `.photoslibrary` bundle) and copies originals/edited files out: "By default, osxphotos will export both the original and the edited image"; tested macOS 10.12.6 through Sequoia with "limited testing" on Tahoe (26.0) and a version table listing 26.0–26.7 and 27.0; "Notably OSXPhotos cannot read shared albums on macOS 26.x"; Python >=3.10 <=3.14 [sourced: https://github.com/RhetTbull/osxphotos README, fetched 2026-11-03].
- Faces/people: the API exposes `PhotoInfo.face_info` ("list of FaceInfo objects representing faces in the photo"), `person_info`, and `persons` (names) [sourced: https://rhettbull.github.io/osxphotos/API_README.html]. The CLI `--sidecar xmp` exports "Face Regions (Metadata Working Group and Microsoft Photo)"; `--exiftool` writes `XMP:PersonInImage`; `--person-keyword` writes person names as keywords [sourced: https://rhettbull.github.io/osxphotos/cli.html]. So named faces with regions ARE recoverable on macOS — the one platform where this is true.
- iCloud-only originals: "Photos that aren't stored locally can be missing from an export" (Optimize Mac Storage); `--download-missing` "uses AppleScript to communicate with Photos," which the README calls "somewhat buggy"; `--use-photokit` is "Highly experimental alpha" [sourced: README and CLI docs].
- Timings (real runs): maintainer, 2024-01-15: "I routinely run osxphotos to update a backup of my 30K image library to a fast external drive and it takes about 1.5 hours" — an incremental update of an existing export, not a full export [sourced: https://github.com/RhetTbull/osxphotos/discussions/1388, 2024-01-15]. User, July 2025, "42,000+" items / ~450 GB library, osxphotos 0.72.1 on macOS 15.5, third full export: "Elapsed time: 2:08:00", "Processed: 49231 photos, exported: 52031, missing: 547, error: 0", with an AppleScript crash ("AppleEvent timed out. (-1712)") on a prior run [sourced: https://github.com/RhetTbull/osxphotos/discussions/1896, 2025-07-22]. (A previously cited "47,508 photos in 1:08:39" run attributed to discussion #1267 was not in that thread and has been removed; see Audit log.)
- 100k-photo projection: ≈4.3 h for a full export of locally-stored originals to a fast external SSD [estimated: linear scaling of the only full-export data point, 49,231 processed items in 128 min (discussion #1896) → 100,000 ÷ 49,231 × 128 min ≈ 260 min ≈ 4.3 h; using the 52,031 exported-file count instead gives ≈ 4.1 h]. The 30K/1.5 h figure is an incremental update and is not used as an input. If originals are iCloud-only, add download time ≈ library_bytes ÷ sustained bandwidth, e.g. an illustrative 300 GB at 50 Mbps ≈ 300 × 8 × 1000 Mb ÷ 50 Mb/s = 48,000 s ≈ 13.3 h [estimated: arithmetic on illustrative inputs 300 GB and 50 Mbps], plus AppleScript fragility.
- Realistic migration path? Yes for users who own a Mac with "Download Originals to this Mac" enabled: it is the only route that yields originals + albums + named faces with regions. It requires a Mac, Full Disk Access, local disk ≥ library size, and hours of wall-clock; it does not help Mac-less iPhone users.

### Q4. Google Photos API after March 31 2025

- Removed scopes: `photoslibrary.readonly`, `photoslibrary.sharing`, `photoslibrary`. Remaining: `photoslibrary.appendonly`, `photoslibrary.readonly.appcreateddata`, `photoslibrary.edit.appcreateddata`. "You can now only list, search, and retrieve albums and media items that were created by your app." Calls relying on removed scopes return "403 PERMISSION_DENIED"; sharing methods likewise. A new "Photos API User Data and Developer Policy" replaced the acceptable-use policy; no post-March-2025 updates appear on the page [sourced: https://developers.google.com/photos/support/updates, fetched 2026-11-03]. Announcement post dated 2024-09-18: the Library API "will focus on accessing and managing photos and videos uploaded by your application" [sourced: https://developers.googleblog.com/en/google-photos-picker-api-launch-and-library-api-updates/, 2024-09-18].
- Picker API: the user selects in the Google Photos app; app polls `sessions.get` until `mediaItemsSet`; `pickingConfig.maxItemCount` default 2000, maximum 2000 ("Values above 2000 will be coerced to 2000") [sourced: https://developers.google.com/photos/picker/reference/rest/v1/sessions, fetched 2026-11-03]. "Base URLs remain active for 60 minutes"; `=d` downloads an image "retaining all the Exif metadata except the location metadata"; `=dv` returns "a high quality, transcoded version of the original video" [sourced: https://developers.google.com/photos/picker/guides/media-items, fetched 2026-11-03]. So a third party cannot enumerate the library; it can only receive ≤2000 user-picked items per session, with GPS stripped from images and videos transcoded.
- Takeout: archive size choice up to 50 GB ("Archives that are larger than the size limit you selected are split into multiple files"); creation "anywhere from a few minutes to a few days", most "the same day"; archives expire after ~7 days and can be downloaded up to 5 times; scheduled exports "every 2 months for one year"; delivery to email link, Drive, Dropbox, OneDrive, Box; Photos-specific non-file metadata, "like comments within Google Photos, are downloaded to a secondary JSON file" [sourced: https://support.google.com/accounts/answer/3024190, fetched 2026-11-03]. Sidecar naming is inconsistent in practice (`.supplemental-metadata.json` and truncated variants; `(1)` suffix misplacement) [sourced: https://exiftool.org/forum/index.php?msg=88112, 2024, community forum]. Ente's importer "reads the JSON metadata sidecar files" and warns "If Google split a media file and its metadata across different ZIPs, the metadata might not be matched correctly" [sourced: https://ente.com/help/photos/migration/from-google-photos].
- Google→iCloud direct transfer: launched 2024-07-10 ("rolling out over the next week"), built on "the open source Data Transfer Project (DTP) technology stack" [sourced: https://dtinit.org/blog/2024/07/10/DTI-members-new-photo-video-tool, 2024-07-10]. Google's "Copy your photos & videos to a service outside of Google" transfers "photos, videos, albums, and descriptions"; excludes Locked Folder, unsaved Memories/creations, the video part of Motion/Live Photos, manually edited metadata/comments, Trash; re-running "may create a new copy"; the page does not name iCloud (the destination dropdown is unnamed) — the iCloud direction rests on the DTI post above and Apple's page below [sourced: https://support.google.com/accounts/answer/9666875, fetched 2026-11-03]. Regions: Apple's page says "over 240 countries and regions" [sourced: https://support.apple.com/en-us/120924, 2024-09-16].
- Google's own DMA compliance report (6 March 2026) confirms the shape of what remains: Takeout "available worldwide"; the Data Portability API "available for end users in all EEA countries, the UK, and Switzerland to port their relevant data to developers. Additionally, it is available for authorized third parties globally." (para 53); "Since 6 March 2025, Google has not made technical/engineering changes to Takeout and the Data Portability API" (para 54) [sourced: https://storage.googleapis.com/transparencyreport/report-downloads/pdf-report-bb_2025-3-7_2026-3-6_en_v1.pdf, 2026-03-06, read via pdftotext 2026-11-03].

### Q5. Apple "Transfer a copy of your data"

- iCloud Photos → Google Photos: "Most transfers take between three and seven days, although some might take up to 30 days"; "This service is available in over 240 countries and regions"; not for child or Managed Apple Accounts; requires 2FA and Advanced Data Protection OFF; "Only the most recent edit of the photo is transferred and not the original version"; "Whenever possible, photos are transferred with their albums" (videos without albums); shared albums, Smart Albums and Live Photos are not transferred; "Duplicates appear as just one photo"; Google caps albums at 20,000 photos; names prefixed "Copy of" [sourced: https://support.apple.com/en-us/118257, page dated 2026-10-09, fetched 2026-11-03].
- Google Photos → iCloud Photos (2024): "JPEG, HEIC, PNG, GIF, TIFF, and BMP photo file types and most MP4 and MOV video file types can be transferred"; metadata "file name, description, file type, and location"; Motion Photos, Live Photos, Memories not transferred; RAW and other unsupported files go to iCloud Drive; items land in an "Import from Google" album; "might take between several hours and a few days"; ADP must be off; re-request "won't add duplicate photo or video files" [sourced: https://support.apple.com/en-us/120924, page dated 2024-09-16, fetched 2026-11-03].
- Apple's March 2026 DMA summary describes the same tool: "through the Data & Privacy Page, users can also select the 'Transfer a copy of your data' option... Currently, this option supports the transfer of photos and videos stored in iCloud to Google Photos, and music playlists in Apple Music to Google's YouTube Music service." (Annex 16, para 6) — i.e., Google Photos is the only photo destination Apple lists [sourced: https://www.apple.com/legal/dma/NCS-March-2026.pdf, 2026-03-07, read via pdftotext 2026-11-03].
- What is lost in both directions: faces/people (never mentioned, not transferred), edit history/originals (Apple sends only latest edit), Live/Motion Photo pairing, shared albums, smart albums; Google→iCloud also drops albums (only an import album is created).

### Q6. Data Transfer Initiative in 2026

- Partners (dues-paying): Amazon, Apple, Ernie App, Google, Meta. Affiliates: Onfabric, Inflection AI, Koodos Labs. Associates: European Internet Forum, Fediforum, Trust Over IP, W3C. "DTI is not a trade association"; no join process documented [sourced: https://dtinit.org/partners, fetched 2026-11-03]. Amazon and ErnieApp joined Jan 2025 [sourced: https://dtinit.org/blog/2025/01/28/year-3-growth, 2025-01-28].
- Homepage: "Over a dozen services are connected today, from Google Photos to Facebook." No list and no onboarding process for new destinations [sourced: https://dtinit.org/, fetched 2026-11-03].
- Data Transfer Project repo: 3.6k stars, 503 forks, 2,012 commits, 19 open issues, 18 PRs; README still says "DTP is early-stage open source code" and "we are actively looking for partner organizations" [sourced: https://github.com/dtinit/data-transfer-project, fetched 2026-11-03]. Maintenance: the `master` branch shows 10 commits between 2026-09-09 and 2026-11-02, most recent 2026-11-02 ("feat(imgur): read base and auth URLs from service config (#1519)", "feat(microsoft): export sha1 for OneDrive photos and videos (#1530)"), plus 2026-09-09 "feat(amazon-photos): add Media vertical importer (#1521)" and a CI release-automation commit 2026-09-15 — so DTP is actively maintained with photo-related work landing in Q3–Q4 2026 [sourced: https://github.com/dtinit/data-transfer-project/commits/master, fetched 2026-11-03].
- Data Trust Registry (DTR): announced 2025-10-07 as "a secure service with a database to hold verified participant information"; Trust Level 1 (organisation details, privacy policy, secure communications) and Level 2, which adds "a third-party data security audit" (the post does not name specific standards; Fabric's Level 2 listing is described as "complete with a SOC2 report"); first listings Koodos Labs (L1) and Fabric.io (L2) [sourced: https://dtinit.org/blog/2025/10/07/announcing-data-trust-registry, 2025-10-07]. Listing does not itself grant access to Apple/Google transfer tools — no source says it does [unknown — none found].
- MCP: DTI (2026-09-16) is "exploring if MCP can facilitate personal data portability"; the only shipped artifact is MCP support for Schemas.Pub (public schemas, not personal data) [sourced: https://dtinit.org/blog/2026/09/16/expanding-ai-capabilities-with-mcp, 2026-09-16].

### Q7. EU DMA Article 6(9)

- Designated core platform services (23): Alphabet — Google Play, Maps, Shopping, Search, YouTube, Android, Ads, Chrome; Apple — App Store, iOS, Safari, iPadOS; plus Amazon, Booking, ByteDance, Meta, Microsoft services. **Neither Google Photos nor iCloud/iCloud Photos is a designated CPS** [sourced: https://digital-markets-act.ec.europa.eu/gatekeepers_en, fetched 2026-11-03]. Article 6(9) obligations attach to designated CPS data, so there is no direct DMA lever on a Photos library.
- Commission developer portal: gatekeepers must provide "continuous and real-time access"; Google's Data Portability API allows access "up to 180 days per authorisation", free; Apple's listed tools are App Store account data transfer, iOS/iPadOS AppMigrationKit, Safari import [sourced: https://digital-markets-act.ec.europa.eu/developer-portal/end-user-data-portability_en, fetched 2026-11-03].
- Google (primary compliance report, read this round): the Data Portability API launched 6 March 2024 "built on the functionalities of Takeout" (para 4); February 2025 added "forward-looking access to data" and date-range filters (para 5); users authorise "a single transfer of a copy of their existing data, or authorize access for a period of time - 30 days or 180 days" (para 24(d)); "The Data Portability API is available for end users in all EEA countries, the UK, and Switzerland... Additionally, it is available for authorized third parties globally." (para 53); "Since 6 March 2025, Google has not made technical/engineering changes" (para 54); footnote 25: "on 11 December, 2025, Google made Pixel and Nest data available via the Data Portability API. This enhancement goes beyond the requirements set out in Art. 6(9) DMA" [sourced: https://storage.googleapis.com/transparencyreport/report-downloads/pdf-report-bb_2025-3-7_2026-3-6_en_v1.pdf, published 2026-03-06, read via pdftotext 2026-11-03]. The API's scope list contains no Google Photos library scope; the only photo scope is `dataportability.maps.photos_videos` [sourced: https://developers.google.com/data-portability/user-guide/scopes, fetched 2026-11-03]. Developers need app verification (brand, use case, demo video, security assessment where required) [sourced: https://developers.google.com/data-portability].
- Apple (primary non-confidential summary, read this round; 290 pages, dated 2026-03-07): Art. 6(9) is served "through its Data & Privacy Page, including continuous and real-time access to the relevant data through scheduled downloads as well as the option to have in-scope data transferred to and used by authorized third parties" (Section 2 para 38); "Since Apple does not collect any iOS or iPadOS data in a way that identifies individual users, neither iOS nor iPadOS data is provided to end users under Art. 6(9) DMA." (Annex 16 para 21) and likewise no Safari data (para 22); data "in .json and/or .csv formats" (para 23); third parties go through "a questionnaire... a review... and a complaint mechanism for denied requests" (para 36); "Apple has developed and enabled a device switching solution in iOS/iPadOS 26.3" (para 37); KPIs reported are counts of App Store-related 6(9) requests and Account Data Transfer API authorisations [sourced: https://www.apple.com/legal/dma/NCS-March-2026.pdf, 2026-03-07, read via pdftotext 2026-11-03]. The Account Data Transfer API covers "App Store information, app install, and push notification activity" for EU, UK and JP users; recurring modes `DAILY_30` and `WEEKLY_180`; download URLs available 3 days, valid 15 minutes [sourced: https://developer.apple.com/documentation/accountdatatransfer, fetched 2026-11-03]. "Eligibility is not limited to providers of alternative app marketplaces" [sourced: https://developer.apple.com/support/account-data-transfer-api-eu]. iCloud Photos appears in the summary only as the pre-existing user-facing "Transfer a copy of your data" tool (Annex 16 para 6, Q5 above); TechCrunch (2024-03-07) likewise notes users "can already request to transfer their iCloud Photos to Google Photos" [sourced: https://techcrunch.com/2024/03/07/apple-will-make-it-easier-to-move-to-android-by-fall-2025, 2024-03-07, press].
- Cross-OS switching: Commission factsheet (2026-05-11) says Apple and Google's cross-OS solution moves "contacts, calendar events, messages, photos, documents" and that Apple "made the relevant documentation available to developers in beta" (AppMigrationKit); this is a device-to-device switch, not a third-party API [sourced: https://digital-markets-act.ec.europa.eu/factsheet-how-dma-making-smartphones-better-interoperability-and-data-portability-case-studies-2026-05-11_en, 2026-05-11]. The Commission's DMA review staff working document adds: "The beta version of the device portability solution was rolled out in December 2025 on both Android and iOS, with the full rollout to users expected in 2026." [sourced: SWD(2026) 123 final, below].
- Uptake and enforcement (primary, read this round): Commission Staff Working Document SWD(2026) 123 final, Brussels 28.4.2026, section 2.1.2: "With regard to Article 6(9) of the DMA, thousands of end users are taking advantage of the data portability solutions across the different gatekeeper platforms to download their data, and around 40 third parties authorised by end users have successfully integrated with the gatekeepers' APIs" [sourced: https://digital-markets-act.ec.europa.eu/document/788ff6d9-f0bf-47d2-80a8-611d5ee5bc51_en (PDF), 2026-04-28, read via pdftotext 2026-11-03]. The Commission's review Q&A names examples: "Around 40 third-party developers, many of them SMEs, like DataPods, Gener8, Hoda, Smart Data Donation Service and Fabric, have successfully integrated with gatekeepers' APIs to port user data." and states "the focus will remain on effective enforcement, regulatory dialogue, and raising awareness" [sourced: https://digital-markets-act.ec.europa.eu/about-dma/dma-review-qa_en, 2026-04-28]. The review itself (COM, CELEX 52026DC0178) was announced 2026-04-28: "The first review of the DMA found that the DMA remains fit for purpose." [sourced: https://digital-markets-act.ec.europa.eu/review-highlights-digital-markets-act-remains-fit-purpose-and-has-positive-impact-2026-04-28_en, 2026-04-28]. No Art. 6(9) non-compliance decision is listed in the SWD or on the Commission's DMA news pages through 2026-06-26 [negative search of the primary documents above]. Italy's AGCM opened a preliminary DMA probe (2026-06-16) into whether Apple lets alternative cloud providers perform full device backups on iOS — interoperability, not 6(9) [sourced: https://www.macrumors.com/2026/06/16/apple-faces-first-italian-dma-probe-icloud/, 2026-06-16, press]. (An earlier line citing a "Macfarlanes" summary with an "enforcement priority through 2027" date had no URL and is withdrawn; see Audit log.)

### Q8. Android

- Scoped storage (Android 10+, enforced for apps targeting Android 11): "Apps that run on Android 11 but target Android 10 (API level 29) can still request the `requestLegacyExternalStorage` attribute... After you update your app to target Android 11, the system ignores the `requestLegacyExternalStorage` flag." With scoped storage, `MediaStore.Files` "shows only the photos, videos, and audio files that your app has created"; the broad "All files access" (`MANAGE_EXTERNAL_STORAGE`) is Play-restricted: "If you target Android 11 and declare All files access, it can affect your ability to publish and update your app on Google Play." [sourced: https://developer.android.com/about/versions/11/privacy/storage, fetched 2026-11-03]. Full media enumeration nonetheless remains available: "To access media files that other apps create, you must declare the appropriate storage-related permissions, and the files must reside in one of the following media collections: MediaStore.Images, MediaStore.Video, MediaStore.Audio" — via `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` (Android 13+) or `READ_EXTERNAL_STORAGE` (older); unredacted GPS needs `ACCESS_MEDIA_LOCATION` ("there is no guarantee that your app has access to unredacted EXIF metadata"); and Google's own doc warns "The `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` permissions are restricted to specific use cases outlined in the Google Play policy. We recommend using the photo picker instead" [sourced: https://developer.android.com/training/data-storage/shared/media, fetched 2026-11-03].
- Android 14 (API 34) adds "Selected Photos Access" (`READ_MEDIA_VISUAL_USER_SELECTED`): the user may grant full access, partial access, or deny; devices upgrading keep prior full grants [sourced: https://developer.android.com/about/versions/14/changes/partial-photo-video-access, fetched 2026-11-03]. Google Play restricts these permissions: apps "may only request" them when "core functionality revolves around broad access to Photos and Videos" and must file a Play Console declaration. Dates: the declaration page says "Starting January 22, 2025, your app must comply" and gives May 28 2025 as the extension-request deadline [sourced: https://support.google.com/googleplay/android-developer/answer/15800983, fetched 2026-11-03]; the policy page says the policy was introduced October 2023 with full compliance mandatory May 28 2025 [sourced: https://support.google.com/googleplay/android-developer/answer/14115180, fetched 2026-11-03]. A backup/gallery app is a plausible qualifying use but the policy does not name "backup" explicitly [unknown].
- Background upload: Doze "Suspends network access" and "Doesn't let JobScheduler run... so WorkManager tasks don't run" until maintenance windows; charging exits Doze [sourced: https://developer.android.com/training/monitoring-device-state/doze-standby]. "If a background work task takes longer than 10 minutes to complete, it's highly likely to be interrupted"; `shortService` must finish in 3 minutes; long transfers should use a foreground service or User-Initiated Data Transfer (UIDT) jobs [sourced: https://developer.android.com/develop/background-work/background-tasks]. UIDT (Android 14+): "may be able to run for an extended period of time as system conditions allow", "unaffected by App Standby Buckets quotas", require a notification, must be scheduled while the app is visible, and the system may stop them for thermal or "longer than necessary" reasons; the user can kill them from Task Manager [sourced: https://developer.android.com/develop/background-work/background-tasks/uidt, fetched 2026-11-03]. Android 15 (API 35) caps `dataSync` foreground services: "The system permits an app's `dataSync` services to run for a total of 6 hours in a 24-hour period, after which the system calls the running service's `Service.onTimeout(int, int)` method"; "The 6-hour time limit is shared by all of an app's `dataSync` foreground services... if the user brings the app to the foreground, the timer resets"; after exhaustion `ForegroundServiceStartNotAllowedException` ("Time limit already exhausted for foreground service type dataSync"); Google's listed alternative is the data-transfer APIs (UIDT) [sourced: https://developer.android.com/about/versions/15/behavior-changes-15, fetched 2026-11-03].
- Immich's Android background-sync problems are typically OEM battery-saver / thermal related: #32058 "[Android] Background backup never runs on devices that report thermal throttling permanently" (closed 2026-10-03); #31637 "[Android] Overheating and battery drain: an asset the server rejects is re-uploaded in full on every backup run, 69 GB sent in 80 minutes" (closed 2026-09-17) [sourced: https://github.com/immich-app/immich/issues/32058 and https://github.com/immich-app/immich/issues/31637, via the repo issue list fetched 2026-11-03].
- Verdict: materially easier than pre-26.1 iOS (full enumeration + user-initiated long transfers with a notification, or up to 6 h/24 h of `dataSync` foreground service per foreground visit), with the residual risks being Play policy review for `READ_MEDIA_*`, the Android 15 6-hour cap, and OEM battery killers. Post-iOS 26.1 the gap narrows, because Apple now offers a system-managed path Android lacks (Android still requires the app's own foreground service/UIDT).
