# A1 — Google removed third-party read access to Photos libraries (March 2025) and this is durable

Skeptic pass, 2026-11-03. Brief: refute first. Tags per README: `[sourced: url, date]`, `[estimated: method]`, `[unknown]`.

Method note: the per-turn WebSearch budget was already exhausted by sibling agents when this pass started (0 of the planned searches ran). All new evidence below comes from direct WebFetch of primary Google, EU, UK CMA, DTI and GitHub pages where a reversal would have to appear, plus the two research files (`platform-access.md`, `byo-ai.md`). Four guessed Google URLs returned 404 (picker/library release-notes, `support/faq`, `support/user-data-policy`, two partner-program paths); their absence is recorded, not treated as evidence.

## The assumption, as stated in v0

"Google actually removed third-party read access to Photos libraries (March 2025) and this is durable (will not be reversed by DMA or policy)."

## Verdict

**holds** — confidence **0.75**.

Precise form that holds: *self-serve developer read access to a user's full Google Photos library (enumerate, search, download arbitrary items) was removed on 2025-03-31, has not been restored on any Google surface as of 2026-11-03, and no regulator has a live lever on it.*

Form that does **not** hold (wording to fix in v1): "removed third-party read access" is too strong. User-mediated and partner-gated read routes remain (Picker API, Takeout, DTP transfers to Apple/Microsoft/Flickr). None of them gives a startup or a third-party AI assistant programmatic library access, so the venture's use of A1 survives, but the sentence should say "self-serve developer read access", not "third-party read access".

## Evidence AGAINST (sought first)

1. **Mediated read access still exists — Picker API.** A user can hand a third party up to 2000 items per session, repeatable: "Defaults to 2000 if not specified." / "Values above 2000 will be coerced to 2000." No album or whole-library selection is documented [sourced: https://developers.google.com/photos/picker/reference/rest/v1/sessions, fetched 2026-11-03]. A community MCP server already uses it as "full library access even after the March 31, 2025 deprecation", with a 10,000 requests/day quota [sourced: https://raw.githubusercontent.com/savethepolarbears/google-photos-mcp/main/README.md, fetched 2026-11-03; community repo]. Weight: weak as refutation — it is user-driven selection, GPS-stripped, 60-min URLs (per platform-access.md Q4), not enumeration.
2. **Takeout still offers scheduled, incremental, machine-deliverable exports.** "Automatically create an archive of your selected data every 2 months for one year"; for Google Photos "you can set up automatic exports of new and updated items, but only if Photos is the only product selected"; delivery to Drive, Dropbox, OneDrive, Box; the Takeout UI accepts URL parameters so an app can "preselect products, the cloud destination, and the export frequency" [sourced: https://support.google.com/accounts/answer/3024190, fetched 2026-11-03]. Weight: moderate for migration (A2-adjacent), weak for A1 — it is a user-initiated bulk archive, not an API.
3. **Google-selected partners DO still get library read.** Google's "copy to a service outside Google" names "your Apple, Microsoft, or Flickr account" as destinations [sourced: https://support.google.com/accounts/answer/9666875, ©2026, fetched 2026-11-03]. The open-source DTP exporter Google's transfer is built on still requests `photoslibrary.readonly` for PHOTOS/VIDEOS/MEDIA export and calls `photoslibrary.googleapis.com/v1/mediaItems:search` and `/albums` [sourced: https://raw.githubusercontent.com/dtinit/data-transfer-project/master/extensions/auth/portability-auth-google/src/main/java/org/datatransferproject/auth/google/GoogleOAuthConfig.java and .../google/photos/GooglePhotosInterface.java, fetched 2026-11-03]; that config file was last changed 2025-07-24 ("Add Synology Photos Importer extensions (#1461)") — i.e. after the scope removal and without touching the export scope [sourced: https://github.com/dtinit/data-transfer-project/commits/master/extensions/auth/portability-auth-google/.../GoogleOAuthConfig.java, fetched 2026-11-03]. Since Google says that scope returns `403 PERMISSION_DENIED` after 2025-03-31 for everyone else, and Apple's transfer page is still live (dated 2026-10-09, per platform-access.md Q5), Google's production transfer must run on an allow-listed client [estimated: inference from the three primaries above; Google publishes no allow-list]. Weight: this is the strongest hit. It shows the removal is a **policy gate, not a technical impossibility** — Google can and does grant full-library read to chosen third parties (Apple, Microsoft, Flickr, and DTP importers such as Synology). No documented application path for a startup exists (platform-access.md Q6: DTP "partner-gated"; DTR "is a trust-verification layer, not an access grant").
4. **Partner program mention.** Google's authorization page still references "the Google Photos APIs partner program" [sourced: https://developers.google.com/photos/library/guides/authorization, fetched 2026-11-03]. Checked: the Library overview defines it as a quota tier only — "You can integrate with the Google Photos APIs without joining the partner program"; it is for apps "likely to exceed the general availability quota limit" [sourced: https://developers.google.com/photos/library/guides/overview, fetched 2026-11-03]. Weight: nil — not an access exception.
5. **DTP is being opened up.** DTI (2026-07-21): DTP now has "a public API interface for even broader interoperability" and "Small companies can connect to DTP server instances without running their own"; DTP is "fully in the public domain" [sourced: https://dtinit.org/blog/2026/07/21/midstride-check-in, 2026-07-21]. Weight: weak today — the post says nothing about Google Photos as a source for non-partners; the DTP README still only says "we are actively looking for partner organizations" with a mailing list, no onboarding process [sourced: https://raw.githubusercontent.com/dtinit/data-transfer-project/master/README.md, fetched 2026-11-03]. This is the item most likely to flip durability (see below).
6. **Regulatory levers searched — none found.** EU: Alphabet's designated CPS are Google Play, Maps, Shopping, Search, YouTube, Android, Ads, Chrome; Apple's are App Store, iOS, Safari, iPadOS; "Neither Google Photos nor iCloud is designated"; the only 2025 change listed is the April 2025 de-designation of Facebook Marketplace; no new designations or market investigations shown for 2025–2026 [sourced: https://digital-markets-act.ec.europa.eu/gatekeepers_en, fetched 2026-11-03]. Google's Data Portability API still has no Google Photos library scope — the only photo scopes are `dataportability.maps.photos_videos` and `dataportability.streetview.imagery` [sourced: https://developers.google.com/data-portability/user-guide/scopes, fetched 2026-11-03]; its release notes end 2025-02-20 and name only `my_activity` and `chrome_history` resource groups [sourced: https://developers.google.com/data-portability/release-notes, fetched 2026-11-03]. UK: the CMA's SMS designation of Google's mobile platform (final decision 2025-10-22; commitments 2026-04-01; steering CR consultation 2026-06-30, responses 2026-08-14) covers "mobile operating systems, native app distribution and mobile browser and browser engine" and mentions no photos, cloud storage or portability [sourced: https://www.gov.uk/cma-cases/sms-investigation-into-googles-mobile-platform, last updated 2026-08-14, fetched 2026-11-03]. DTI's 2025–2026 blog index has no post on new photo destinations or Google Photos API access [sourced: https://dtinit.org/blog/, fetched 2026-11-03].

Net of the "against" column: items 1–2 are routes the venture can use for migration, not refutations; item 3 is the real finding (access is granted by Google to chosen parties, so "removed" is a choice Google can un-make); item 5 is the only observed trend toward reversal and it is early; item 6 came up empty.

## Evidence FOR

1. **Primary removal notice.** Scopes `photoslibrary.readonly`, `photoslibrary.sharing`, `photoslibrary` removed; "All changes take effect March 2025"; "These changes will take effect March 31, 2025"; remaining scopes `photoslibrary.appendonly`, `photoslibrary.readonly.appcreateddata`, `photoslibrary.edit.appcreateddata`; **no dated entry after 2025-03-31** on the updates page [sourced: https://developers.google.com/photos/support/updates, fetched 2026-11-03].
2. **Current scope table confirms no full-read scope.** "After March 31, 2025, you will only be able to access content created by your application."; "If your app needs to select photos from a user's library, use the new Picker API." [sourced: https://developers.google.com/photos/library/guides/authorization, fetched 2026-11-03]. Library overview: "The Library API lets you manage content within the user's library that was created by your app." [sourced: https://developers.google.com/photos/library/guides/overview, fetched 2026-11-03].
3. **No reversal signal on any Google developer surface.** Google Developers Blog, Google Photos category: 10 posts shown, all Oct 2026, none about Photos APIs [sourced: https://developers.googleblog.com/en/search/?technology_categories=Google+Photos, fetched 2026-11-03]. Picker get-started page has no 2025–2026 feature additions [sourced: https://developers.google.com/photos/picker/guides/get-started-picker, fetched 2026-11-03].
4. **Google's own DMA compliance report**: "Since 6 March 2025, Google has not made technical/engineering changes to Takeout and the Data Portability API" (para 54); only addition was Pixel/Nest data on 2025-12-11 (fn 25), described as going "beyond the requirements" [sourced: https://storage.googleapis.com/transparencyreport/report-downloads/pdf-report-bb_2025-3-7_2026-3-6_en_v1.pdf, 2026-03-06, as read in platform-access.md Q4/Q7].
5. **Downstream corroboration**: no ChatGPT Google Photos connector; community MCP servers fall back to Picker (byo-ai.md Q4) [sourced: byo-ai.md, 2026-11-03]. Gemini reads Google Photos as a first-party connected app only (byo-ai.md Q4).
6. **Direction of travel is tightening, not loosening**: Play's photo-permission policy made full compliance mandatory 2025-05-28 (platform-access.md Q8) [sourced: https://support.google.com/googleplay/android-developer/answer/14115180, as read in platform-access.md].

## What observable fact would flip the verdict

Any one of these, from a primary source, flips to **broken**:
- A new or restored Library API scope that reads media items not created by the app, appearing on https://developers.google.com/photos/support/updates or the authorization page.
- A `dataportability.photos.*` (or similar) scope on https://developers.google.com/data-portability/user-guide/scopes, or a Google DMA report paragraph adding Photos to the Data Portability API.
- Google Photos designated as a core platform service on https://digital-markets-act.ec.europa.eu/gatekeepers_en, or a Commission/CMA decision naming Google Photos data access.
- A documented self-serve path for a non-partner to run DTP exports from Google Photos (e.g. DTI publishing destination onboarding that includes Google Photos as a source), or Google's "copy to a service outside Google" dropdown adding a non-giant destination.

Would flip to **partial** (durability only): Picker `maxItemCount` raised materially above 2000 or album/whole-library selection added; a DTI post announcing Google Photos source access via the "public API interface" for DTR-listed companies.

Would raise confidence toward 0.9: a Google policy page stating that full-library scopes will not be reinstated, or a second full year with no change on the updates page (next check: 2027-03-31).
