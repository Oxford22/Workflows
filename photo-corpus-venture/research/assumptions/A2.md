# A2 — iOS full-library export to a third party, or macOS as the path

Written 2026-11-03 by a skeptic subagent whose brief was to refute the assumption. Tagging per README: `[sourced: url, date]`, `[estimated: method]`, `[unknown]`.

Method note: the shared WebSearch budget for this run was already exhausted when this check started (7 queries attempted, 0 performed). All evidence below comes from 24 direct WebFetch reads of primary pages (Apple developer docs via the `/tutorials/data/*.json` endpoint, Apple support pages, App Store listings, GitHub issues/discussions of the shipping backup apps, osxphotos repo) plus the already-audited `research/platform-access.md`. Refutation-targeted reads were done first (Ente/Immich iOS issue threads, osxphotos macOS 26/27 breakage, Apple App Review guidelines, Apple's extension restrictions, iCloud-original download failures); confirming evidence was weighed afterwards.

## Assumption

**A2.** "Apple PhotoKit / iOS background constraints still allow a third party to export a user's full library (originals + metadata) with acceptable friction; or macOS is a viable path."

Decomposed into the three claims that must all be true for A2 to hold as written:

- A2a. A third-party iOS app can read the whole library — originals and metadata — including iCloud-only originals.
- A2b. It can move that library off the device with "acceptable friction" (no multi-night babysitting; not dependent on an API nobody ships).
- A2c. If iOS fails, macOS is a viable alternative path for the same user.

## Verdict

**partial** — confidence **0.72** [estimated: judgment; the three sub-claims split holds / broken-in-practice / viable-but-fragile, and the two main uncertainties (whether the iOS 26.1 extension's unpublished limits allow a 100k-asset initial upload, and what share of target users own a Mac) are both unresolved].

- A2a: **holds, with one hole.** Full-library enumeration and original bytes are documented and used by shipping apps. **People/face names and regions are not exposed on iOS** — "originals + metadata" is not fully satisfiable on iOS.
- A2b: **broken in practice today, feasible on paper.** Twelve months after Apple shipped the Background Resource Upload extension, no major backup app (Ente, Immich, Google Photos, Dropbox) has shipped it; every one of them still tells users to keep the app open and plugged in for a large initial backup. The only shipping adopter is an "experimental" 31-star app that needs an extra proxy server to work around Apple's restrictions. The extension's inflight job limit and per-invocation runtime limit are unpublished, so no one can say from the docs whether a 100k-asset initial upload completes unattended.
- A2c: **viable, Mac-only, fragile.** osxphotos exports originals, albums and named faces with regions, and a 49k-item full export is a ~2 h job — but it breaks on every macOS release (three schema/path breakages fixed in Sep 2026, one AMFI breakage open since Jul 2026, a 70k-photo Tahoe export that threw 27,119 errors), cannot read shared albums on macOS 26.x, and only helps users who own a Mac with originals downloaded.

"Partial" rather than "broken" because the pieces exist and work (PhotoKit read, Apple's extension in one shipping app, osxphotos on a Mac). "Partial" rather than "holds" because the friction clause fails on the evidence: the actual user experience on iOS in 2026 is "keep the app open overnight, plugged in, on Wi-Fi, for nights until it finishes," and the one API that would fix that has not been adopted by anyone with a product team.

### 2. Apple's iOS 26.1 / 27 extension is real but restricted, undocumented in its limits, and has one adopter

- Requirements and limits, verbatim from Apple's article: "Your app must have full library access before enabling the extension." / `BackgroundUploadURLBase` "The system requires this key for network access validation." / "The system enforces a limit on inflight jobs. When you reach this limit, job creation throws `limitExceeded`." / "Retrying a job counts toward the inflight job limit." / "The system manages the extension life cycle and may terminate your extension at any time due to resource pressure." / "Keep each invocation within the runtime limit." (no number) / "The system may purge downloaded resources due to disk space constraints." / Server must implement the IETF draft resumable-upload protocol: respond to `OPTIONS` with `Upload-Limit`, send `104 (Upload Resumption Supported)`; "Your API must include both the `OPTIONS` preflight check and the `104` informational response." / "In iOS, this feature isn't available in Simulator" [sourced: https://developer.apple.com/tutorials/data/documentation/photokit/uploading-asset-resources-in-the-background.json, read 2026-11-03].
- `jobLimit`: "The maximum number of unacknowledged upload jobs allowed." / "This includes jobs that are in-flight and those that have succeeded or failed." Numeric value: not on the page. Availability iOS 26.1+, macOS 27.0+ [sourced: https://developer.apple.com/tutorials/data/documentation/photos/phassetresourceuploadjob/joblimit.json, read 2026-11-03]. Value: [unknown — Apple does not publish it].
- Per-invocation runtime limit value: [unknown — Apple does not publish it; Developer Mode "removes the extension runtime limit on each invocation" only for test builds].
- API churn inside one year: `setUploadJobExtensionEnabled(_:)` introduced 26.1, **deprecated in 27.0** ("Use -enableUploadJobExtensionWithOptions:error: and -disableUploadJobExtensionWithError: instead"); `PHBackgroundResourceUploadExtension` deprecated in 27.0 in favour of `PHBackgroundResourceUploadJobExtension`; `PHAssetResourceUploadJob.resource` deprecated in 27 [sourced: https://developer.apple.com/tutorials/data/documentation/photos/phphotolibrary/setuploadjobextensionenabled(_:).json and the article above, read 2026-11-03]. An adopter who built on 26.1 is already on a deprecated surface.
- Consent: 9to5Mac 2025-10-24: "Some of aspects of the new feature will require express user consent." The article does not say which, and Apple's enable-method pages mention no user prompt [sourced: https://9to5mac.com/2025/10/24/ios-26-1-third-party-photos-backup-background/, 2025-10-24, press; Apple pages above]. What the consent UI is: [unknown].
- Only known shipping adopter: YAIIU ("Yet Another Immich iOS Uploader"), self-described "experimental", 31 stars, 4 forks, 117 commits, AGPL; "iOS 26.1+ for background uploads"; "due to iOS limitations with background upload extensions" the user must deploy an additional `immich-proxy` server between device and Immich; "this app needs to connect to GitHub for network access validation" [sourced: https://github.com/FawenYo/YAIIU and its README, read 2026-11-03]. Users in #23245 report it "works in the background after the initial sync" — i.e., even the adopter is described as background-after-initial, not unattended-initial [sourced: https://github.com/immich-app/immich/discussions/23245, 2026-01-30 → 2026-02-13].

### 3. "Originals + metadata" is not fully reachable on iOS: no People/faces API

- Apple's Photos framework topic index (read 2026-11-03) contains no class, protocol or symbol for people, persons, faces or recognized subjects; the eleven topic groups are Shared photo library, Asset retrieval, Asset loading, Asset metadata, Asset resource management, Background resource upload extensions, Live Photos, Errors, Deprecated errors, Classes, Protocols [sourced: https://developer.apple.com/tutorials/data/documentation/photos.json, read 2026-11-03]. Corroborates the 2020 community statement "there is not an API to access people data in PhotoKit" [sourced: https://developer.apple.com/forums/thread/126711, Jun 2020, community]. A family-archive product that promises "cluster faces across generations" would have to re-derive on iOS what the user already curated in Apple Photos.

### 4. iCloud-only originals are the real throughput bottleneck, and it is outside the app's control

- Apple: under Optimize Storage "your device keeps smaller versions, and the full-resolution originals stay in iCloud"; "When you need more device storage, iCloud Photos optimizes your library, starting with photos and videos you access least." Whether Optimize is the default on iPhone: [unknown — the page does not say] [sourced: https://support.apple.com/en-us/108782, read 2026-11-03].
- Immich #32747 (opened 2026-10-27, **open**, Bug/mobile/Backlog): iPhone 16 Pro, library "over 40,000 items" with many iCloud-only originals; reporter saw "over 1,300 open connections"; maintainer agg23 2026-10-27: "The Immich app itself doesn't open any connections to iCloud" — PhotoKit does the fetch; app limits itself to 3 concurrent uploads; reporter: many iCloud downloads "never finish, even on a fast connection"; maintainer says the team is reviewing its iCloud handling [sourced: https://github.com/immich-app/immich/issues/32747, 2026-10-27, read 2026-11-03].
- Immich discussion #29676 (2026-07-07, closed as cross-ref to #32747): reporter observed 20–40 concurrent iCloud downloads, after which "all downloads timeout and fail"; claims iCloud tolerates only "1-2 concurrent downloads" and that exceeding it got an IP "rate limited or temporarily blocked" (a user claim, not an Apple statement); 3–4 at a time worked; a 1 Gbps link did not help [sourced: https://github.com/immich-app/immich/discussions/29676, 2026-07-07, read 2026-11-03].
- Ente: "for backup, Ente always retrieves the original, full-resolution photo or video directly from iCloud." / "Keep the device connected to the internet while that backup finishes." [sourced: https://ente.com/help/photos/faq/backup-and-sync, read 2026-11-03].

### 5. App Review pushes against full-library access

- App Store Review Guideline 5.1.1(iii) Data Minimization: "Apps should only request access to data relevant to the core functionality of the app and should only collect and use data that is required to accomplish the relevant task. Where possible, use the out-of-process picker or a share sheet rather than requesting full access to protected resources like Photos or Contacts." 5.1.2(vi): data from "Photo APIs" "may not be used for marketing, advertising or use-based data mining, including by third parties" [sourced: https://developer.apple.com/app-store/review/guidelines/, read 2026-11-03]. A backup/migration app has a defensible core-functionality claim (the extension itself requires full access), so this is a review risk, not a bar; but a product whose pitch is "index everything with VLMs and expose to any AI model" sits closer to 5.1.2(vi)'s "use-based data mining" language than a pure backup app does. ### 6. The macOS path is Mac-only and breaks on every OS release

- osxphotos README: "If apple changes the database format this will likely break."; "Notably OSXPhotos cannot read shared albums on macOS 26.x."; "For macOS 26.0 / Tahoe, limited testing has been done to ensure basic functionality works."; Photos' AppleScript interface (needed for `--download-missing`) "is somewhat buggy and you may find that Photos crashes."; "The `--download-missing` option for `osxphotos export` does not work correctly with burst images." [sourced: https://github.com/RhetTbull/osxphotos README, read 2026-11-03].
- 2026 breakages (issue titles verbatim): "macOS 27 beta: PhotosDB fails to build, 'no such table: Z_33ASSETS' (actual join table is Z_34ASSETS, model_ver=270008501)" (#2165, closed 2026-09-20); "macOS 27.0: could not find search db: .../database/search/psi.sqlite" (#2207, closed 2026-09-20); "get_system_library_path() returns None on macOS 27: SystemLibraryPath moved to group container plist" (#2237, closed 2026-09-27); "macOS 27: search_info.activities always empty" (#2221, closed 2026-09-23); "AMFI 'Unrecoverable CT signature issue' blocks pyobjc/photoscript import on macOS 26.5.2 (Tahoe), installed via uv" (#2175, **open** since 2026-07-18, every command fails including `osxphotos version`); "Crash with osxphotos export --download-missing … SIGABRT" (#2253, closed 2026-10-11); "tahoe 26.4 - [Errno 24] Too many open files" (#2138, **open**) [sourced: https://github.com/RhetTbull/osxphotos/issues (search: macOS 26 / Tahoe / macOS 27), read 2026-11-03].
- #2138 detail: export of 69,952 photos on Tahoe 26.4; after the v0.75.8 mitigation the run still logged "27,119 errors out of 69,952 photos" (reporter: "the number of errors/missing files is too high"); worked only after downgrading Python 3.14 → 3.13.13; maintainer: fix "comes at a performance hit that slows down overall export time" [sourced: https://github.com/RhetTbull/osxphotos/issues/2138, 2026-04-15 → 2026-04-25, read 2026-11-03].
- Structural: it is a reverse-engineered SQLite reader maintained by one person ("I've done extensive testing against my own Photos library but that's a single data point"), not an Apple API. It requires a Mac, Full Disk Access, local disk ≥ library size, and "Download Originals to this Mac" (or the buggy AppleScript path). Share of target users who own a Mac: [unknown]. A consumer product cannot ask a non-technical family member to install Python and run a CLI; the macOS "path" is really "build and maintain our own Photos.sqlite reader and ship it in a notarized Mac app," inheriting the same per-release breakage.

### 7. Apple's own export tool does not help a third party

- "Transfer a copy of your data": only Google Photos is named as a destination; "Most transfers take between three and seven days," some up to 30; "Only the latest edit of a photo is sent, not the original"; shared albums, smart albums, Live Photos not transferred; Advanced Data Protection must be off; not for child or Managed accounts (page dated 2026-10-09) [sourced: https://support.apple.com/en-us/118257, 2026-10-09, read 2026-11-03]. Apple's March 2026 DMA report lists Google Photos as the only photo destination [sourced: https://www.apple.com/legal/dma/NCS-March-2026.pdf, 2026-03-07, per platform-access.md]. No regulatory lever: neither iCloud Photos nor Google Photos is a designated DMA core platform service [sourced: https://digital-markets-act.ec.europa.eu/gatekeepers_en, per platform-access.md].

## Evidence FOR

- **Full read is documented and real.** With `.authorized` status PhotoKit exposes every `PHAsset` and `PHAssetResourceManager` returns original bytes; `isNetworkAccessAllowed = true` fetches iCloud-only originals per request [sourced: https://developer.apple.com/documentation/photos/phimagerequestoptions/isnetworkaccessallowed and .../phassetresourcerequestoptions/isnetworkaccessallowed, per platform-access.md]. Ente, Immich, Google Photos and Dropbox all ship full-library iOS backup on exactly this basis.
- **Apple built the extension specifically for this use case.** "PhotoKit's Background Resource Upload extension enables apps to deliver seamless cloud backup experiences. The system manages uploads on your app's behalf, processing them in the background even when people switch to other apps or lock their devices." It handles iCloud originals itself ("The system automatically downloads asset resources before processing"), is resumable, supports download-only jobs, and the article explicitly contemplates initial full-library uploads ("Return `.processing` during initial library uploads when you have remaining assets to process") [sourced: Apple article JSON above, read 2026-11-03]. This is a stronger platform position than Android, which still requires the app's own foreground service / UIDT with a 6 h per 24 h `dataSync` cap on Android 15 [sourced: https://developer.android.com/about/versions/15/behavior-changes-15, per platform-access.md].
- **The API is broadly installed.** 79% of all iPhones and 86% of iPhones introduced in the last four years run iOS 26, "As measured by devices that transacted on the App Store on June 7, 2026" [sourced: https://developer.apple.com/support/app-store/, 2026-06-07 measurement, read 2026-11-03]. Share specifically on ≥26.1: [unknown — Apple reports only the major version].
- **One app proves it works end to end.** YAIIU ships on the App Store using `PHBackgroundResourceUploadExtension`; its author 2026-01-30: the app "keeps uploading in the background"; the hardcoded `BackgroundUploadURLBase` "only verifies connectivity" so the real server can differ [sourced: https://github.com/immich-app/immich/discussions/23245, 2026-01-13/30; https://github.com/FawenYo/YAIIU, read 2026-11-03]. The blockers Immich cites (fixed URL, raw body) are an incumbent's integration-cost problem, not an obstacle for a new app that designs its server for Apple's protocol from day one.
- **Incumbents' non-adoption has a benign reading.** Ente's maintainer says the extension "requires us to adopt a very different architecture than the current encrypt + upload pipeline" (E2EE client-side encryption is incompatible with the system uploading raw asset bytes) [sourced: https://github.com/ente-io/ente/issues/7127, 2025-11-17]. Immich's blockers are self-hosted-URL and multipart-API specifics. Google and Dropbox already have Standby/Overnight modes and little incentive. None of these reasons applies to a greenfield app with a fixed cloud endpoint and no client-side encryption.
- **Keep-the-app-open works, if slowly.** Dropbox Overnight uploads and Google Photos Standby mode are shipped, supported paths; Immich users finish 200k-file initial syncs by leaving the device on overnight [sourced: Dropbox 2026-09-17 and Google help pages per platform-access.md; https://github.com/immich-app/immich/discussions/23245, 2026-02-04]. Whether "several nights plugged in" is "acceptable friction" is a product judgment, not a technical impossibility.
- **macOS does deliver originals + albums + named faces.** osxphotos exposes `face_info`, `person_info`, `persons` and writes face regions / `XMP:PersonInImage` to sidecars [sourced: https://rhettbull.github.io/osxphotos/API_README.html and cli.html, per platform-access.md]. A real full export: ~42k items / ~450 GB, "Processed: 49231 photos, exported: 52031, missing: 547, error: 0" in "Elapsed time: 2:08:00" on macOS 15.5 [sourced: https://github.com/RhetTbull/osxphotos/discussions/1896, 2025-07-22]. 100k-photo projection ≈ 4.3 h for local originals [estimated: 100,000 ÷ 49,231 × 128 min ≈ 260 min; single data point]. The maintainer closed all three macOS 27 schema/path breakages within 1–8 days of macOS 27.0 (#2207, #2165 closed 2026-09-20; #2237 closed 2026-09-27) [sourced: osxphotos issues list, read 2026-11-03] — the format is reverse-engineerable and has been re-engineered within days for every release since 10.12.

## What observable fact would flip the verdict

To **holds** (any one of these, primary-sourced):
1. A major consumer backup app — Google Photos, Dropbox, OneDrive, Amazon Photos, Ente or Immich — ships Apple's Background Resource Upload extension and its help page drops the "keep the app open" instruction for initial backup.
2. Apple publishes the numeric `jobLimit` and per-invocation runtime limit, and they are large enough that a 100k-asset / 300 GB initial upload is shown (by a measured run) to complete unattended within a few days.
3. Apple adds a People/persons API to PhotoKit (a `PHPerson`-class symbol appears in the Photos framework index), closing the metadata hole.

To **broken** (any one):
1. Apple's App Review begins rejecting full-library backup/migration apps under 5.1.1(iii) or 5.1.2(vi), or an Apple policy statement restricts the extension to a vetted set of partners.
2. The extension is pulled or its restrictions tightened (e.g., requires Apple-approved `BackgroundUploadURLBase` domains) in iOS 27.x.
3. Apple changes the Photos library format in a way osxphotos cannot follow for more than one release cycle (e.g., encryption of `Photos.sqlite`), removing the macOS fallback.
4. The iCloud-original fetch path is shown (by an Apple statement or a measured run) to throttle to a rate that makes a 300 GB iCloud-only library infeasible on-device (e.g., < 5 Mbps sustained ≈ > 5.5 days) [estimated: 300 × 8 × 1000 Mb ÷ 5 Mb/s = 480,000 s ≈ 5.6 days; illustrative threshold].
