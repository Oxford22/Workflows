## One line

An iOS app that indexes the job photos a small contractor already has in the camera roll (and the ones crew texted them), groups them into jobs by place and time, answers "show me the Smith rough-in" in plain language, and exports a one-tap evidence packet (originals + EXIF table + SHA-256 + map) for the warranty call, the deposit fight or the 10-year latent-defect claim — without changing how anyone shoots.

## Wedge (first use case adopted without changing habits; the first 10 minutes; day-1 value for ONE user; day-7 value)

**First use case, no habit change.** The owner keeps shooting with the iPhone camera and keeps texting the crew. The app reads the library in place (PhotoKit `.authorized` enumerates the whole library; `PHAsset.location` and creation date are standard properties, iOS 8+) [sourced: developer.apple.com photos/phasset/location.json fetched 2026-11-03; research/platform-access.md Q1]. Nothing is uploaded to get value; originals stay in iCloud.

**The first 10 minutes (one owner, one phone).**
1. Install, grant full Photos access (one system prompt). Tap "Index". The run is a user-initiated `BGContinuedProcessingTask` with a Live Activity — the only sanctioned long-running path on iOS 26/27; unattended overnight runs do not exist [sourced: Apple docs via research/ios-feasibility.md Q2].
2. Indexing from local previews (optimized-storage copies observed at ~1536×2048, no iCloud download needed where a local copy exists) [sourced-secondary: budgethomelab.com 2026-06-06 via ios-feasibility.md Q4]. Wall-clock for 30,000 assets with MobileCLIP-S2 embeddings and no faces: ~15 min, ~22 min derated; adding full-library OCR takes it to hours, so OCR runs only on frames a text detector flags [estimated: ios-feasibility.md Q3 inputs; the 10 ms thumbnail-fetch assumption is unmeasured]. A contractor library size: [unknown]; the 4-week demo measures ten real ones.
3. By minute ten the owner sees a "Jobs" list: clusters of photos by location and time, labelled with a reverse-geocoded street address (one MapKit geocode per cluster, not per photo, because geocoding is rate-limited per app — "at most one geocoding request for any one user action"; `CLGeocoder` is deprecated in 26.0 in favour of MapKit) [sourced: developer.apple.com corelocation/clgeocoder.json fetched 2026-11-03]. Personal photos (home, truck, lunch) fall into a "not a job" bucket by location and are never shown.

**Day-1 value for ONE user.** Retrieval the owner could not do before: "water heater serial plate, Elm St job" hits the OCR'd data plate; "the trench before backfill at the Oak St job" hits the embedding. Then the first evidence packet: pick a job, tap Export → PDF with the unmodified originals, an EXIF table (capture time, GPS, device), a SHA-256 per file and a map. The hash matters because FRE 902(14) (2017) lets "data copied from an electronic device, storage medium, or file" self-authenticate "by a process of digital identification", and the committee note says such data "are ordinarily authenticated by 'hash value'" [sourced: law.cornell.edu/rules/fre/rule_902 fetched 2026-11-03]. State small-claims courts do not follow the FRE; whether a hash-attested packet changes outcomes there: [unknown].

**Day-7 value.**
- (a) Crew phones join the company: each crew member's app indexes their own camera roll and syncs metadata + 512 px thumbnails + embeddings (not originals) to the company index, so the owner's "Elm St" job now shows the apprentice's photos too.
- (b) Photos received by iMessage from the crew are indexed on the owner's phone, but whether iMessage preserves GPS on received photos is [unknown: not verified this round; the demo tests it on device], which is why crew-phone pooling, not message scraping, is the design.
- (c) The office connects the company index to Claude as a custom connector (Claude Free: one custom connector, prefilled install link, mobile use) [sourced: research/assumptions/A6.md verdict table] and asks "which jobs did we do on Oak St in 2023?" — the MCP endpoint is a two-day wrapper (research/byo-ai.md Q5), and that is fine: it is a feature here, not the wedge.

## Why now (dated changes since 2024, each tagged)

1. **2026-09-14, iOS 27 Foundation Models:** on-device model gains image input (`ImageAttachmentContent` introducedAt 27.0), the `Tool` protocol lets the model call "a tool that searches a local or online database", a Spotlight-powered local RAG tool and an `OCRTool` are built in, and Claude/Gemini are drivable through the same `LanguageModel` session with tool calling (beta/preview) [sourced: WWDC26 241/339, Apple docs JSON, anthropics/ClaudeForFoundationModels README, firebase.blog 2026-06-09 via research/ios-feasibility.md Q1]. Natural-language "show me the Smith rough-in" over a local job index costs the developer $0 on device; PCC is free below 2M downloads with an unpublished daily cap [sourced: developer.apple.com/private-cloud-compute via ios-feasibility.md Q1]. Caveat: the on-device LLM needs an Apple-Intelligence device, plausibly 50–60% of active iPhones [estimated: ios-feasibility.md Q5]; the core loop (clustering, OCR via Vision, MobileCLIP embeddings, embedding search) runs on any iPhone that runs the app and must not depend on it.
2. **2026-09-09, CompanyCam MCP Server beta** for ChatGPT and Claude [sourced: companycam.com blog via verticals.md §2.1 Q3]: the incumbent validated "assistant over job photos" and simultaneously showed the office-assistant layer is theirs for their customers — so this variant's defensible part is the index of photos CompanyCam never sees, not the MCP layer.
3. **2026-09-14, Siri AI** ships "surfacing relevant information from a user's messages, emails, photos, and more", English-first, iPhone 16+ (iOS 27 Apple Intelligence baseline), not in the EU on iOS [sourced: apple.com/newsroom 2026-09-14 fetched 2026-11-03]. It raises every owner's expectation that photos are searchable by sentence — and leaves the job entity, crew pooling and evidence export unbuilt (see Platform risk).
4. **2025 (iOS 26), `BGContinuedProcessingTask`** — a user-initiated, Live-Activity-visible long-running task, the first sanctioned way to index tens of thousands of assets in one go [sourced: ios-feasibility.md Q2].
5. **2026-10-26, Android ML Kit GenAI Embeddings API (alpha)** on-device image+text embeddings, plus Function Calling preview [sourced: developers.google.com/ml-kit release notes via ios-feasibility.md Q7] — index parity for crew Androids is now a port, not a research project; the assistant layer is not at parity.
6. **Cost collapse of server-side captioning:** a 22,000-image caption pass is $0.69 (Gemini 2.5 Flash-Lite batch) or $1.36 (Claude Haiku 5.5 batch) on 2026-11-03 price pages [estimated: research/unit-economics.md Q3 table] — cheap enough to caption only the flagged "data plate / permit / invoice" frames server-side when a phone lacks the on-device model.
7. **2025-08-22 CompanyCam Series C** (PitchBook: $415M at $2B [sourced-secondary: siliconprairienews 2025-11-22]) and **2026-03-02 Beam acquisition** with "tens-of-thousands" of businesses [sourced: companycam.com/press via verticals.md §2.1] — the incumbent is scaling upmarket (Enterprise 50+ users on the pricing page); a review reports a 2026-09-17 price rise to $79/$149/$299 monthly [sourced-secondary: theroofingbrief.com 2026-10-19; conflicts with the page as rendered, [unknown]]. A $12/mo product for nonemployers is a different company than a $2B seat-and-storage business.
8. **Aug 2026, G.T. v. Samsung (7th Cir.):** on-device face templates the company never holds are outside BIPA's "possess/collect" [sourced: research/face-regulation.md Q1]. This variant goes further and ships no face recognition at all (jobs are places, not people), which removes the Illinois/Texas exposure the consumer variants carry.

Counter-signal: none of these is unavailable to CompanyCam, Jobber or Housecall Pro; items 1 and 4 are Apple plumbing for every developer (research/ai-why-now.md §6 scores OS-level VLM APIs 7 but "weakly defensible").

## Product (core loop; explicitly NOT in v1)

**Core loop.** (1) Enumerate PhotoKit assets → (2) cluster on (lat, lon, capture time) into job candidates; label with a reverse-geocoded address; learn from the owner's one-tap confirmations ("this is 1427 Elm, the Nguyen job"; "not a job") → (3) per asset: MobileCLIP embedding on the Neural Engine, Vision text detection, OCR on text frames, perceptual hash + SHA-256 at index time → (4) search box and Siri-style sentence search backed by an on-device Foundation Models `Tool` over the local index, with plain embedding/keyword search as the fallback on non-Apple-Intelligence phones → (5) evidence packet export (PDF + originals zip, EXIF table, hashes, map, optional notes) → (6) company pooling: crew apps push metadata + thumbnails + embeddings to a company index; owner sees one job view → (7) remote MCP server (OAuth) exposing `search_photos`, `list_jobs`, `get_job`, `export_packet` for the office's assistant or invoicing tool.

**Retention logic the product sells.** Statutes of repose: CA 10 yrs latent (CCP §337.15), TX 10 yrs extendable to 12 (CPRC §16.009), IL 10 yrs, FL 7 yrs, NY none [sourced: sdvfenchurch survey current as of 08/2024 via trades-and-reddit.md A3]; a Texas construction lawyer advises keeping "progress photos and field reports" 13 years after substantial completion [sourced: ftworthconstruction.lawyer 2025-10-23]; NSPE: repose + 3 years [sourced: NSPE 2016 via verticals.md §2.1]. No statute requires photo retention; the driver is litigation defense [verticals.md §2.1 Q2 verdict]. The product therefore keeps a server-side copy of the *evidence packet* (not the library) for 15 years when the owner exports one — the one thing the camera roll and a phone upgrade will not do for them.

**Explicitly NOT in v1.** A capture app (no in-app camera, no stamps burned into pixels); project management; estimating/invoicing; face recognition or people search; video indexing beyond keyframes; Android assistant features (Android *indexing* client is v1.1, see Buildability); storing originals; a web gallery for homeowners.

## Platform risk (the obvious feature Apple/Google/incumbent could ship; why this survives or doesn't)

**Apple.**
- What ships: natural-language search ("car next to lake") on iPhone 15 Pro/16+ since 2024-10-28; auto-organized Collections "like recent days or trips" (iOS 18) [sourced: apple.com/newsroom 2024-10-28 via trades-and-reddit.md A4; apple.com/newsroom 2024-06 iOS 18 fetched 2026-11-03]; Siri AI surfaces "information from a user's ... photos" (2026-09-14). Live Text search of text inside photos since iOS 15 [unknown: not re-verified this round; treat as likely, so OCR alone is not a differentiator].
- What is left, argued from feature absence (trades-and-reddit.md A4): a job/customer entity (a trip is not an address with a customer name), cross-phone pooling outside a 6-person family Shared Library (ios-feasibility.md Q6), an evidence export with hashes, and any endpoint a third-party invoicing tool can call.
- Apple has never shipped a small-business vertical feature in Photos; the risk that it does is low, but a "group by address" collection would erode the day-1 grouping value. Survival: partial — grouping is the hook, pooling + packets + MCP are the product.
**Google.** Irrelevant on iOS; on Android, Google Photos' third-party library read is gone (research/assumptions/A1.md holds) and Ask Photos is closed AI; the Android client reads MediaStore directly (platform-access.md Q8).
**CompanyCam (the real risk).**
- It already imports camera-roll photos: the Magic Uploader pulls "photos taken at the Project's address", 100 at a time, no video, and "Every photo and video in CompanyCam lives in a Project, so open one or create a new one before you start" [sourced: help.companycam.com/…/6828411 fetched 2026-11-03]. It ships MCP (beta). It could ship "index my whole camera roll into auto-created projects" in a quarter.
- Why it has not: its FAQ sells the opposite ("your job photos are stored in the cloud, so they don't clog your camera roll") and its revenue is seats × unlimited storage at $63–199/mo; retro-indexing a phone without ingesting it creates no storage lock-in and serves a $144/yr customer it has not pursued in ten years (penetration ≤4.8% of the small-trades base [estimated: trades-and-reddit.md A2]).
- That is a business-model reason, not a capability one; if the long tail turns out to be worth it, they can follow. Jobber and Housecall Pro ("Photo reports & annotations" on Essentials [sourced: housecallpro.com/pricing via trades-and-reddit.md A2]) are the same risk one step removed. Honest score: this variant survives an incumbent copy only if the pooled company index and the 15-year packet archive have made switching painful before the copy ships — roughly 18 months of head start, and the incumbents already have the customer relationship.

## Compounding asset

- **The job graph:** address ↔ customer ↔ photos ↔ dates ↔ crew ↔ (via MCP) invoices, confirmed by the owner's taps over years, across phones that get replaced. Rebuildable from the phones, but only while the phones and the people are still around; after a phone upgrade or an apprentice leaving, the company index is the only copy of "who shot what where". Weak-to-moderate: a competitor could re-index the same camera rolls.
- **Attested timeline:** SHA-256 and capture metadata recorded at index time, with the index-time timestamp. A late installer can hash old photos but cannot backdate when the hash was first recorded. Whether courts or adjusters value "we recorded this hash in March 2027" over a bare EXIF date: [unknown].
- **The packet archive:** retained 15 years server-side, growing with every dispute; the one artefact that outlives the camera roll, the phone and the iCloud plan. This is the switching cost, and it is zero on day 1.
- Not an asset: the MCP layer (54,763 active registry servers [sourced: research/byo-ai.md Q5]); the embedding index (<$1 to rebuild, unit-economics.md Q3).

## Buildability (4-week demo spec for 2 engineers; ugliest technical risk)

- **Week 1 (iOS, engineer A):** PhotoKit enumeration, (lat, lon, time) clustering (DBSCAN with ~75 m / 36 h thresholds [estimated: starting parameters, tuned on real libraries]), one MapKit reverse-geocode per cluster, "Jobs" list, "not a job" bucket, confirm/rename taps persisted in SQLite.
- **Week 1 (server, engineer B):** Postgres + pgvector company index; per-asset metadata/thumbnail/embedding ingest; OAuth.
- **Week 2 (A):** `BGContinuedProcessingTask` indexing with Live Activity, resumable in chunks; MobileCLIP-S2 Core ML embedding; Vision text detection → `VNRecognizeTextRequest` on flagged frames; on-device vector search.
- **Week 2 (B):** remote MCP server (`list_jobs`, `search_photos`, `get_job`, `export_packet`), tested as a Claude custom connector.
- **Week 3 (A):** search UI; Foundation Models `Tool` over the local index on Apple-Intelligence devices, embedding search elsewhere.
- **Week 3 (B):** evidence packet: originals fetched with `isNetworkAccessAllowed` at export time (per-job, small), EXIF table, SHA-256, map, PDF; 15-year packet store on B2.
- **Week 4 (both):** second phone joins a company; pooled job view; run on ten real contractor libraries (recruited from the owner's network, not Reddit); measure clustering precision/recall, index wall-clock, share of iCloud-only assets with no local preview, and whether iMessage-received photos carry GPS. Android indexing client (MediaStore, LiteRT MobileCLIP port, Play policy declaration) is v1.1, weeks 5–10 [estimated: ios-feasibility.md Q7 says index parity is a port].
**Ugliest technical risk: job segmentation on a mixed personal/work camera roll.** GPS is absent or 50–200 m off indoors and in dense streets [estimated: typical urban GPS error; unmeasured here]; two jobs on one street, a return visit a year later, and a crew member's photos texted without GPS all break (lat, lon, time) clustering; an evidence packet that includes the wrong house's photos is worse than no packet. Mitigations (owner confirmations, address OCR from permits and mailboxes, "same place as job X" prompts) are UI work with no published accuracy benchmark; precision on real libraries is [unknown] until week 4. Second risk: PhotoKit throughput assumptions (10 ms thumbnail fetch) are unmeasured (ios-feasibility.md Q3), and the Neural Engine is now restricted in the background without an entitlement whose request process is undocumented (ios-feasibility.md Q2) — the design assumes foreground/Live-Activity indexing only.
