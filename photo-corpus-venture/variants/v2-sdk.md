## One line

Replace the "select your photos" step inside photo-book, print, tribute and genealogy apps with an embedded, on-device picker that indexes only the window the product needs (last 12 months, an event, a person the user taps), collapses bursts and duplicates, ranks by Apple's free aesthetics score, balances people, and hands the host a ready selection — never storing originals and never computing a face template off the user's device — sold to the companies that already earn billions from the order the selection feeds (CEWE €864.5M, Shutterfly ~$1B-class, Vista $1.8B); honest ceiling as a component vendor is **$5–15M ARR**, not $100M.

## Wedge (first use case adopted without changing habits; the first 10 minutes; day-1 value for ONE user; day-7 value)

**The platform-policy answer first, because it sets the shape.** The brief's SDK ("one on-device index shared across every memory-product app") cannot ship on iOS: "An app group allows multiple apps developed by the same team to access one or more shared containers" [sourced: developer.apple.com/documentation/xcode/configuring-app-groups via memory-product-sdk.md Q6]; cross-team sharing is user-mediated and per item (share sheet, document picker, `Transferable` drag/drop) [estimated: inference in memory-product-sdk.md Q6; Transferable not separately verified]. The host app, not the SDK, holds the Photos grant and the App Review justification: 5.1.1(iii) "Where possible, use the out-of-process picker or a share sheet rather than requesting full access to protected resources like Photos"; 5.1.2(i) requires disclosure "where personal data will be shared with third parties, including with third-party AI"; a third-party SDK must ship a privacy manifest and, if listed, a signature [sourced: developer.apple.com guidelines and privacy-manifest pages via memory-product-sdk.md Q6]. On Android the SDK's `<uses-permission>` merges into the host manifest, so the host owns the Play declaration ("Full policy compliance is mandatory for all developers", 2025-05-28) [sourced: developer.android.com/build/manage-manifests; support.google.com/googleplay/android-developer/answer/14115180 via memory-product-sdk.md Q6]. **So: restructured.** Three shapes, in order of priority:
1. **Embedded picker (per host, on-device).** A Swift/Kotlin package that runs inside the host's own container under the host's existing PhotoKit/`READ_MEDIA_IMAGES` grant, indexes only the window the product needs, and returns a selection. Nothing is "indexed once" across apps; each host re-indexes its window. Allowed under the host's own core-functionality claim (Chatbooks already opens the Camera Roll by default; Shutterfly already offers device selection) [sourced above]; App Review outcome for a host adding a third-party on-device indexing SDK is [unknown — no rejection or acceptance record found].
2. **Server-side curation over already-uploaded sets** (the CEWE/Vista web route: 2.60bn photos/yr already leave the phone for CEWE's production [sourced: CEWE AR 2025]) — dedupe, burst collapse, aesthetics, event grouping; **no face templates of living people server-side** (Shutterfly itself settled a BIPA face-grouping class action for $6,750,000, approved 2021-09-09 [sourced-secondary: Willkie 2021-09-23 via research/face-regulation.md Q1]). Priced per 1k images against Everypixel/Rekognition; weakest shape because every named host already runs this in-house.
3. **Reference app** — the organizer workbench from `current.md` plus a consumer "picker" that exports via share sheet into any vendor; a sales tool and test bed, not the business.

**First use case, no habit change.** The host already has a "choose photos" screen; the SDK is a drop-in replacement for that screen (`presentCuratedPicker(window: .lastMonths(12), target: 60)`), returning asset identifiers the host already handles. End users keep their existing app; nothing migrates; no second app.

**The first 10 minutes (one host engineer).** Add the package; declare the privacy manifest entries; call the picker from the existing selection screen; receive a selection object. The reference integration in the organizer workbench and a sample photo-book app ship with it. Index wall-clock for a 12-month window at 200 photos/month [estimated: research/unit-economics.md Q2 assumption] = 2,400 assets × 76 ms central (thumbnail fetch 30 + embedding 30 + face detection 10 + embedding 6) ≈ **3 min central, ~1.2 min floor, ~4.5 min derated** [estimated: research/ios-feasibility.md Q3 Scenario A per-image inputs × 2,400], inside a user-initiated foreground session — not the 38–57-minute whole-library session that sank v1-federation, because the window is bounded by the product (a yearbook, an event, "photos of this person").

**Day-1 value for ONE user (the host's PM).** A measurable A/B on the one screen they own: time-to-first-page, selection abandonment, completed orders. Honest: the lift is [unknown]; the only public claim is Mixbook's self-reported "time to order in half" after building the same thing in-house [sourced: Mixbook PR 2026-06-11].

**Day-7 value.** The "ask the family" link: the host sends relatives a no-install web link to contribute photos to the same book/tribute (the Tukios mechanic, which Tukios already ships for funeral homes [sourced: estate.md Q8]); contributed photos are deduped against the keeper's selection on the keeper's device; no contributor face template is computed anywhere but the keeper's device, and living people are named only after the keeper taps and the subject consents (research/face-regulation.md Q7 architecture items 1–2). Export carries EXIF and, if the host wants it, XMP `PersonInImage` for the dead or consented [sourced: ios-feasibility.md Q9].

## Product (core loop; explicitly NOT in v1)

**Core loop (inside the host app, on device).**
1. **Window** — the host names the product's need: date range, an event the user picks on a calendar, or "people like this one" (the user taps a face). No whole-library index.
2. **Index** — PhotoKit thumbnails from the locally cached optimized copies (~1536×2048 observed) [sourced-secondary: budgethomelab 2026-06-06 via ios-feasibility.md Q4]; pHash + burst/edit/resolution-variant collapse (the dedupe rules from `current.md` step 3); SigLIP2-class embedding; Vision face rectangles + AdaFace (MIT) embeddings → anonymous on-device clusters [sourced: ai-why-now.md Q3]; Vision aesthetics score [sourced above]; OCR only on frames flagged with text.
3. **Rank** — target count N; diversity across clusters/people/days; aesthetics; the host's page template (e.g., 20 pages × 3) as a constraint.
4. **Pick** — the user sees the N proposal plus "more like this" per person/day; one tap per swap. Selection returned as asset identifiers plus EXIF; originals are fetched by the host's existing upload code (`isNetworkAccessAllowed` per request [sourced: platform-access.md Q1]).
5. **Ask the family** — contribution link (web upload to the host's existing media endpoint, or ours as a proxy); dedupe against the keeper's set on the keeper's device.
6. **Learn** — anonymised keep/swap/discard events (no pixels, no templates) returned to our ranking model with host consent and disclosure under 5.1.2(i).

**Explicitly NOT in v1.** A cross-app shared index (impossible on iOS, Wedge); any server-side face template of a living person; storing originals (index-only, research/unit-economics.md Q7); naming living people without recorded subject consent (face-regulation.md Q7); Google Photos library access (does not exist: A1); whole-library background indexing (ios-feasibility.md Q2); a consumer brand of our own; Windows/desktop; print fulfilment; the hosted family vault from `current.md`.

## Platform risk (the obvious feature Apple/Google/incumbent could ship; why this survives or doesn't)

- **Apple's picker is already most of the product.** `PHPickerViewController` "runs out of process", "doesn't need direct access to the photos library", "won't prompt for access", has "built-in support for search just like the photos app", supports multi-select, and Apple's guidance is "for most apps that only want photo and video data you don't need to use PhotoKit at all" [sourced: https://developer.apple.com/videos/play/wwdc2020/10652/, fetched 2026-11-03]; iOS 17 added inline/compact embedding, continuous selection and the Options menu, with "please avoid requesting photo library access unless it's really necessary" [sourced: https://developer.apple.com/videos/play/wwdc2023/10107/, fetched 2026-11-03]. Whether the picker's search covers People names is not stated in either transcript; the `PHPickerFilter`/`PHPickerConfiguration` reference pages returned 404 at the documentation JSON endpoint on 2026-11-03 [unknown]. The one-slide kill: Apple adds "Suggested for you" / "Best of this year" sorting to the picker. Everything the SDK does except burst collapse and page-aware balancing is then free and permission-less to every host.
- **Google's Picker** already lets the user pick inside Google Photos with Google's own search and face groups; the host receives ≤2,000 GPS-stripped items [sourced: platform-access.md Q4]; Google supplies curation to Fujifilm's store rather than buying it [sourced: memory-product-sdk.md Q1].
- **Apple's App Intents/Transferable path does not make this unnecessary — but not for a reason that helps us.** The `.photos` app-schema domain lets a third-party photo *app* expose its own `asset`/`album`/`recognizedPerson` entities to Siri; it does not expose Apple Photos' People to third parties, and the photos-domain `search`/`openAsset` schemas are deprecated [sourced: developer.apple.com app-schema-domain-photos.json via research/assumptions/A4.md For #8]; Transferable is per-item drag/drop [estimated: memory-product-sdk.md Q6]. So a host still cannot query "Grandma" from Apple's index — it must build or embed its own, which is the SDK's opening, and also why every large host has already built one.
- **Hosts build.** Mixbook (2026-06), CEWE MAIC (2025, "rolled out to all of the Company's subsidiaries"), Shutterfly Autofill "Best Photos" (2026-10-30), Chatbooks Smart Select, Google/Fujifilm (2026-09) [sourced: memory-product-sdk.md Q3, Q5]. Survival argument: dedupe-and-balance quality, the BIPA-safe face posture, and cross-platform (iOS+Android+web) parity are product work a distressed Shutterfly or a 100-person Mixbook may prefer to rent; counter: CEWE's charter forbids third parties touching images, and Mixbook already shipped. Honest: platform risk is high and incumbent build risk is higher; the defensible slice is hosts too small to build and too large to ignore — Chatbooks, Tinybeans, tribute/memoir companies, retail photo — whose combined order volume is [unknown] and plausibly small.
- **App Review.** A host that today uses the picker and switches to full-library access for our SDK invites 5.1.1(iii) scrutiny; probability [unknown]. Mitigation: the SDK also runs in "picker mode" over user-selected sets (no new grant), losing people-balance and window indexing.

## Compounding asset

- **Per host**: integration, A/B history and the ranking model tuned on that host's keep/swap telemetry (no pixels) — switching back to in-house costs a re-tune, not a migration. Moderate.
- **Across hosts**: a selection-quality model trained on anonymised outcomes from many products (which bursts got kept, which page counts converted) that no single host sees — the only asset here that a host cannot rebuild alone. Size of the signal: [unknown] until two hosts are live.
- **Consent and provenance records** for contribution links (who contributed what, under which disclosure) — useful to hosts under 5.1.2(i)/BIPA, cheap to copy.
- **Honest**: the index is rebuilt per window per host and is worthless after the order; the models are commodity (SigLIP2 Apache, AdaFace MIT, Vision aesthetics free); MCP/assistant layers are commodities (54,763 active registry servers [sourced: byo-ai.md Q5]). What compounds is distribution across hosts, and the host list is short.
