# Gap track R5 — On-device indexing without migration (iOS 27 / Android / macOS)

Written 2026-11-03; repaired 2026-11-03 after audit (see "Audit log" at the end). Variant under test: the app indexes the user's *existing* library on device (CLIP-style embeddings, faces, OCR, optional LLM captions) and never migrates originals; the index is queried by an on-device or third-party model through Apple's Foundation Models framework. All web access dated 2026-11-03 unless stated. Apple documentation pages are JavaScript-rendered; where the HTML returned only a title, the `developer.apple.com/tutorials/data/documentation/*.json` endpoint for the same page was read and is cited.

### Q1. Foundation Models framework (iOS/macOS 27)

**On-device image input: yes, from OS 27.** WWDC26 session 241 ("What's new in the Foundation Models framework"): "the on-device model is also gaining Vision capabilities"; "Simply insert an image attachment into your prompt, together with text."; "Image attachments can be created from a variety of types including; UIImage, NSImage, CGImage Core Image types, CoreVideo Pixel Buffers, and file URLs."; "The model supports images in any size and aspect ratio"; "larger images will consume more tokens and incur more latency." [sourced: https://developer.apple.com/videos/play/wwdc2026/241/, WWDC26 (June 2026)]. The framework article "Analyzing images with multimodal prompting": "The framework supports several image types to include in your prompts, like CGImage, CIImage, CVPixelBuffer, and image URLs."; "The framework performs the necessary scaling and color conversions before passing an image to the model"; "Perform image analysis with the on-device model first. If you determine that more reasoning or context is necessary for the task, initialize LanguageModelSession using PrivateCloudComputeLanguageModel." [sourced: https://developer.apple.com/tutorials/data/documentation/foundationmodels/analyzing-images-with-multimodal-prompting.json]. `ImageAttachmentContent` is introducedAt 27.0 (round-0 finding, ai-why-now.md Q1). Framework availability: "To use Apple Foundation Models, people need a device that supports Apple Intelligence." [sourced: https://developer.apple.com/tutorials/data/documentation/foundationmodels.json]. Context: "The on-device model offers 4k, and with PCC you get 32K"; code comment "8192 on 27.0 (newer devices)" [sourced: https://developer.apple.com/videos/play/wwdc2026/319/, WWDC26].

**PhotoKit → image attachment.** PHImageManager returns a UIImage, and `Attachment` accepts UIImage/CGImage/CVPixelBuffer (above), so a PhotoKit thumbnail can be attached without an intermediate file [estimated: inference from the two API surfaces; no Apple sample found that does exactly this].

**Third-party providers and images.** `LanguageModel` protocol (introducedAt 27.0 everywhere): "Implement this protocol to create a bridge between a model and the framework."; conforming types listed: `PrivateCloudComputeLanguageModel`, `SystemLanguageModel`; requirements include `supportsDataAttachmentType(_: UTType) async throws -> Bool` and `capabilities: LanguageModelCapabilities` [sourced: https://developer.apple.com/tutorials/data/documentation/foundationmodels/languagemodel.json]. `LanguageModelCapabilities`: "When a model doesn't support a capability, the framework can refuse to dispatch incompatible requests to the executor and throw an `unsupportedCapability` error" [sourced: .../languagemodelcapabilities.json]. Anthropic's package: "The package conforms Claude to the framework's `LanguageModel` protocol, so you drive it with the same `LanguageModelSession` API you use for Apple's on-device model — `respond(to:)`, streaming, guided generation, and tool calling all work the same way."; "Each model declares what it accepts — sampling parameters, effort levels, adaptive thinking, structured output, and image input."; "A schema or an image needs every model in the chain to support it."; platforms "iOS 27, macOS 27, visionOS 27, or watchOS 27 (beta)"; "Beta ... APIs may change before general availability"; Apache 2.0 [sourced: https://github.com/anthropics/ClaudeForFoundationModels README, read 2026-11-03]. Package version: the README's install snippet is `.package(url: "https://github.com/anthropics/ClaudeForFoundationModels.git", from: "0.1.0")` — a SwiftPM minimum, not a stated release; the repository's tags run 0.1.0 (2026-06-08) through 0.2.3 (2026-10-07), nine tags in all [sourced: https://github.com/anthropics/ClaudeForFoundationModels/tags, read 2026-11-03]. Google: "Starting with iOS 27, macOS 27, iPadOS 27, watchOS 27, and visionOS 27" Gemini is available through the `LanguageModel` protocol "in preview starting today"; requests "routed through Firebase AI Logic"; prompts can include images, audio, video and PDFs; tool calling supported [sourced: https://firebase.blog/posts/2026/06/apple-foundation-models-gemini/, 2026-06-09]. So: images to Claude/Gemini through the same session API — **yes, in beta/preview**, gated by each model's declared capabilities.

**Credentials and billing for third-party models.** Session 241: "if you use third party server models, you'll probably have to deal with both authentication and billing."; "you'll typically be billed per-token when using 3rd party models" [sourced: WWDC26 241]. ### Q2. Core AI and the Background Inference entitlement

**What it is.** `com.apple.developer.background-tasks.continued-processing.inference`, Boolean, default NO, introducedAt 27.0 on all platforms (iOS, iPadOS, macOS, tvOS, visionOS, watchOS as listed on the entitlement page): "An entitlement that lets a background task run inference on the Neural Engine."; "This entitlement works with `BGContinuedProcessingTask`, which lets your app's critical inference work finish on the Neural Engine even when your app moves to the background before the task completes."; "The system also requires the entitlement for any Neural Engine access while your app is in the background, regardless of whether it's running a continued background task. You can perform inference with Core AI, Core ML, or Metal Performance Shaders Graph." [sourced: https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.background-tasks.continued-processing.inference.json]. iOS 27 release notes: "The system now restricts background access to the Neural Engine, similar to GPU usage restrictions."; "Access to the Neural engine when your app is in the background requires the new entitlement" [sourced: https://developer.apple.com/tutorials/data/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes.json]. **This is a restriction that did not exist before iOS 27, not a new grant** [estimated: inference from the release note's "now restricts" plus one developer report]. Developer report (no Apple reply in thread): "In iOS 26, Core ML reliably submits inference requests targeting the Neural Engine in the background. In iOS 27 Seed 1, this capability is currently broken." [sourced: https://developer.apple.com/forums/thread/831934, Jun 2026; 1 reply, 0 Apple replies]. On macOS the picture is explicitly unclear: a DTS engineer, asked about ANE/GPU use from a daemon or system extension, wrote "that iOS advice isn't directly applicable to macOS. iOS doesn't have the equivalent of the global execution context we use for `launchd` daemons on the Mac." and "If it might get done on the GPU or NE, I'm much less confident. You're straying into the world of implementation details" [sourced: https://developer.apple.com/forums/thread/820379, Jul 2026, DTS Engineer reply]. The same thread quotes the macOS release note: "Neural Engine memory usage is now attributed to your app process instead of the system" [sourced: thread 820379, quoting Apple release notes].

**How to request it: [unknown].** The entitlement page says nothing about a request process; the sibling GPU entitlement `com.apple.developer.background-tasks.continued-processing.gpu` ("The entitlement the system requires for a continuous background task to use the GPU.", iOS/iPadOS introducedAt 26.0, no device/chip restriction stated on the page) is enabled as an Xcode capability ("enable the Background GPU Access capability on your app's target") [sourced: https://developer.apple.com/tutorials/data/documentation/bundleresources/entitlements/com.apple.developer.background-tasks.continued-processing.gpu.json; https://developer.apple.com/tutorials/data/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados.json]. A previously cited claim that Background GPU is "iPad-only / M3+ per Apple DTS" could not be traced to a readable page and is withdrawn — device restriction for the GPU entitlement: [unknown]. One developer PR (2026-10-07, repository since renamed from joeblau/voice to joeblau/choff; the old URL redirects) states "The spike ... found that the `continued-processing.inference` entitlement named in ... does not exist in the iOS 27.2 SDK, and that the real behaviour can only be measured with the background probe on an iPhone." and "That measurement is still pending."; the "spike" is an internal issue (#22) not readable here [sourced: https://github.com/joeblau/choff/pull/112, 2026-10-07; single unverified report]. Two oddities to weigh: it contradicts Apple's entitlement page (introducedAt 27.0) and the iOS 27 release notes quoted above, and it names an "iOS 27.2 SDK" on 2026-10-07, three weeks after iOS 27.0 shipped on 2026-09-14 [sourced: https://www.apple.com/newsroom/2026/09/siri-ai-a-profoundly-more-capable-and-personal-assistant-is-here/, 2026-09-14] — whether a 27.2 SDK existed then is [unknown]. Treat the PR as a flag to test on device, not as evidence the entitlement is absent. Apple developer-forum search for the entitlement string returned no matching thread (the search tokenised "continued" and returned unrelated "Continuity" threads) [sourced: https://developer.apple.com/forums/search?q=continued-processing.inference, 2026-11-03]; a search for "neural engine background entitlement iOS 27" surfaced only threads 831934/832048 and 820379 above [sourced: https://developer.apple.com/forums/search?q=neural%20engine%20background%20entitlement%20iOS%2027, 2026-11-03].

**What the host task allows.** `BGContinuedProcessingTask` (introducedAt 26.0): "A task that starts in the foreground and can continue running in the background as needed."; "The system displays the progress of this task in a Live Activity and a person can cancel it"; "The system can terminate a continuous background task abruptly depending on run-time conditions"; "The system prioritizes the termination of tasks that reflect minimal or no progress" [sourced: https://developer.apple.com/tutorials/data/documentation/backgroundtasks/bgcontinuedprocessingtask.json]. Article: "your app needs to run the task only in response to someone's action, such as tapping a button."; "critical work that can take minutes or more"; "The system cancels a `fail` task right away if it can't begin processing the task immediately, for example, when the system reaches a maximum number of concurrent tasks."; "The system cancels any running tasks if a person closes the app in the app switcher" [sourced: performing-long-running-tasks JSON]. WWDC25 227: "Continue processing tasks always start with an explicit action that someone performs in your app"; "People don't expect tasks to start automatically, even if they've set a preference in your app before."; "tasks that do not report any progress will be expired"; "if that progression is slower than expected, the system will prompt the initiator, asking if they want the work to continue." [sourced: https://developer.apple.com/videos/play/wwdc2025/227/]. Developer-forum thread with DTS replies (created Nov 2025, replies dated by a quoted log line 2026-10-29 and relative "3d–6d" on 2026-11-03): expiry is final — "No. The idea is that the API is specifically extending foreground time, so it wouldn't really make sense to 'resume' it later."; opening the Camera expires the task even with regular progress — "Yes, this is expected behavior. The camera generates significant system load ... Duet shuts down other activity (including the continued processing task)"; "There isn't anything you can do to prevent it"; queued resubmission on expiry is "probably not reliable enough to be useful" [sourced: https://developer.apple.com/forums/thread/806668, DTS Engineer replies]. The thread gives no duration cap. **No maximum runtime is published [unknown].** WWDC26 transcript lines: "Meet Core AI" (324) does not mention the entitlement [sourced: https://developer.apple.com/videos/play/wwdc2026/324/]; "Integrate on-device AI models into your app using Core AI" (326) mentions background only for model delivery — "I'll use Background Assets for this."; "I did this with my model and created a background asset for each compiled model." — and contains no sentence with "Neural Engine", "entitlement" or "BGContinuedProcessingTask" [sourced: https://developer.apple.com/videos/play/wwdc2026/326/, transcript read 2026-11-03]. So no WWDC26 session line about Background Inference was found [unknown].

**Scheduled (unattended) overnight runs.** `BGProcessingTask` "run only when the device is idle" and is terminated when the user starts using the device (round 0, platform-access.md Q2). WWDC25 227 narration: "If a task doesn't need to run immediately, consider deferring it until the device is charging."; "a great task may elect to only run when the device is on charger and connected to network."; the property `request.requiresExternalPower = true` appears in the session's code sample for a processing task, not as a narrated recommendation [sourced: https://developer.apple.com/videos/play/wwdc2025/227/]. With the new entitlement a processing task may use the ANE, but its runtime budget is unpublished [unknown]; whether the entitlement requires charging: [unknown — not stated on the entitlement page, release notes, or any forum thread read]. Apple's own Photos face clustering "runs periodically, typically overnight during device charging" [sourced: https://machinelearning.apple.com/research/recognizing-people-photos, 2021-07-28] — a system-privileged daemon, not a third-party budget.

**Verdict on "overnight indexing of 20–50k assets".** Not supported as an unattended job by any documented mechanism: the only long-running path is user-initiated, visible in a Live Activity, cancelable, expirable (final on expiry; killed by Camera use per DTS), and (for ANE) dependent on an entitlement whose request process is undocumented and whose presence in the shipping SDK one developer disputes. The realistic design is "tap Index, leave the phone on charge with the app's Live Activity running", in chunks, resumable. Developer reports of a shipped photo indexer using this path: none found [unknown].

### Q3. Throughput and the 30,000-photo wall-clock

**CLIP-class encoders (Apple-published, phone-measured).** Paper setup: "iPhone12 Pro Max with iOS 17.0.3. Batch size is set to 1 for all the models." Table 7 image/text encoder latency: MobileCLIP-S0 1.5/1.6 ms, S1 2.5/3.3, S2 3.6/3.3, B 10.4/3.3; Table 12 input resolution: MobileCLIP-B 224×224, S0/S1/S2 256×256 [sourced: https://arxiv.org/html/2311.17049v2, v2 2024-04-01, Tables 7 and 12]. Apple's Core ML export card repeats the same latencies (S0 1.5+1.6, S1 2.5+3.3, S2 3.6+3.3, B 10.4+3.3 ms) with no newer-device figure [sourced: https://huggingface.co/apple/coreml-mobileclip README, created 2024-10-21]. Repo table adds MobileCLIP2-S3 8.0, S4 19.6, L/14 57.9 ms (image); device named only as "iPhone12 Pro Max" in the highlights; MobileCLIP2 released 2025-08-28; code MIT, weights "Apple ML Research Model TOU" [sourced: https://github.com/apple/ml-mobileclip]. MobileCLIP2 abstract: "3-15ms latency and 50-150M parameters"; S4 "improves on DFN ViT-L/14 at 2.5× lower latency" [sourced: https://arxiv.org/abs/2508.20691, 2025-08-28]. Latency on iPhone 15/16/17: [unknown — Apple publishes none]; the iPhone 12 Pro Max numbers are a lower bound for per-image cost on newer phones [estimated: newer ANEs are not slower; no measurement]. **Reconciliation with the secondary 20–40 ms figure:** blakecrosley gives "image embedding 20–40 ms" on iPhone 16 Pro without naming the model and describes its table as "derived from public Apple benchmarks and developer-reported measurements ... order of magnitude" [sourced: https://blakecrosley.com/blog/vision-framework-built-in, 2026-05-02; secondary/derived]; Apple's 3.6 ms is a Core ML model-execution benchmark at batch 1 that excludes image decode, resize to 256 px and the request round-trip. The two are not the same quantity; this file uses 3.6 ms as the floor and 30 ms (midpoint of the secondary end-to-end range) as the central per-image embedding cost. Concurrency caveat: a developer measured "a single prediction on the ANE: about 2.8 ms" on an iPhone 17 Pro Max, iOS 27.0.1, and reports that concurrent Core ML predictions are serialized on iOS 27 ("latency is about N × single-call time") where macOS 26.4.1 showed a concurrency gain; 0 replies, no Apple response [sourced: https://developer.apple.com/forums/thread/850110, created ~2026-10-13 ("3w" on 2026-11-03)]. So per-image ANE cost cannot be hidden by running encoders in parallel on iOS 27 [estimated: inference from that single report].

**Faces.** Apple (2021): "On recent iOS hardware, face embedding generation completes in less than 4ms."; "runs end-to-end on the Apple Neural Engine" [sourced: Apple ML Research 2021-07-28; five years old, treated as a floor]. Vision `VNDetectFaceRectanglesRequest` per-frame latency: "5-15 ms" on iPhone 16 Pro [sourced: blakecrosley 2026-05-02; secondary/derived]. No Apple-published ms figure for face detection found [unknown]. Core ML face-embedding ports exist on the Hub — e.g. "ArcFace LResNet100E-IR — CoreML (fp16)", "Input: faceImage — 112x112 RGB image", "Output: embedding — 512-d float vector", "mlprogram / fp16, iOS 17+" [sourced: https://huggingface.co/RuiSumida/ArcFace-R100-CoreML README, created 2026-06-10] — but the card states no latency; three "mobile-facenet-coreml-v2" repos (created 2026-07-02) have no README; Hub search for "arcface coreml" returned one model, "facenet coreml" four [sourced: Hugging Face Hub search via connector, 2026-11-03]. **Latency of an ArcFace/AdaFace Core ML port on an iPhone: [unknown — no model card or benchmark found].** No Vision API named "VNGenerateFaceSegmentation…" was found in the docs read; [unknown].

**OCR.** `VNRecognizeTextRequest` is free and on-device; Apple's WWDC19 demo explicitly declines to give numbers ("the times that you see are not necessarily representative") [sourced: https://developer.apple.com/videos/play/wwdc2019/234/]. Secondary: "OCR (1 page receipt) 150-300 ms" on iPhone 16 Pro [sourced: blakecrosley 2026-05-02, derived]. OS 27 also exposes an `OCRTool` to the LLM [sourced: WWDC26 241].

**Thumbnail delivery.** `requestImage(for:targetSize:...)`: "Photos loads or generates an image of the asset at, or near, the size you specify"; "Photos may provide an image that is slightly larger than the target size—either because such an image is already cached or because it can be generated more efficiently"; "Depending on the options you specify and the current state of the asset, Photos may download asset data from the network."; async requests may deliver first "a low-quality image suitable for displaying temporarily" flagged by `PHImageResultIsDegradedKey` [sourced: https://developer.apple.com/tutorials/data/documentation/photos/phimagemanager/requestimage(for:targetsize:contentmode:options:resulthandler:).json]. `.fastFormat`: "Photos provides only a fast-loading image, possibly sacrificing image quality."; "Photos calls your resultHandler block once. If a high-quality image cannot be loaded quickly, the result handler provides a low-quality image." [sourced: .../phimagerequestoptionsdeliverymode/fastformat.json]. `PHImageResultIsInCloudKey`: "If true, no image was provided, because the asset data must be downloaded from iCloud." [sourced: .../phimageresultisincloudkey.json]. `isNetworkAccessAllowed` defaults to false (round 0; confirmed by a forum reply: "By default requestImage... is local unless you set networkAccessAllowed to YES." [sourced: https://developer.apple.com/forums/thread/63826, Oct 2016 reply]). Field behaviour with network disallowed on an iCloud-only asset, as reported by a developer: "1) Local result handler is called for a degraded image at thumbnail size, the image is present, all is fine. ... 3) Local result handler is called a second time for a non-degraded / isInCloud result with a nil image." [sourced: https://developer.apple.com/forums/thread/63826, 2016; community, not Apple]. So `.fastFormat` on an iCloud-optimized asset does return the local degraded thumbnail — **verified only by this 2016 community report; pixel size not stated** [unknown]. Apple does not document the pixel size of the locally cached thumbnail [unknown]; see Q4 for the field figure on the optimized copy. Per-request fetch time from the local cache: [unknown — no benchmark; PHCachingImageManager exists to batch-preload].

**Wall-clock for 30,000 photos on an iPhone 15/16 [estimated].** Inputs: N = 30,000; thumbnail fetch + HEIC decode + resize t_fetch = 10 ms/image floor, 30 ms central [estimated: assumption; no measurement — the single largest uncertainty; a 1536×2048 HEIC must be decoded and downscaled to 256 px for CLIP and to ~1024 px for faces, which the Apple benchmark excludes]; embedding floor 3.6 ms (MobileCLIP-S2, Apple, iPhone 12 Pro Max, batch 1) / central 30 ms (midpoint of secondary 20–40 ms end-to-end); MobileCLIP2-S4 19.6 ms (Apple, same device); face detection 10 ms (midpoint of 5–15 secondary); faces per photo 1.5 × <4 ms = 6 ms [estimated: 1.5 is an assumption]; OCR 250 ms (midpoint of secondary 150–300). Sustained-load derating ×1.5 for thermal/scheduling on a phone [estimated: assumption; no sustained-ANE benchmark found; iOS 27 ANE serialization per thread 850110 means no parallel speed-up either].
- Scenario A (S2 + faces, no OCR): floor (10 + 3.6 + 10 + 6) = 29.6 ms/image → 888 s → **~15 min (floor)**; central (30 + 30 + 10 + 6) = 76 ms → 2,280 s → **~38 min; ~57 min derated**. The 15-minute figure is a floor built from batch-1 model benchmarks, not a central estimate.
- Scenario B (S4 + faces + OCR on every image): floor (10 + 19.6 + 10 + 6 + 250) = 295.6 ms → 8,868 s → **~2.5 h**; central (30 + 30 + 10 + 6 + 250) = 326 ms → 9,780 s → **~2.7 h; ~4.1 h derated**. OCR dominates; running OCR only on images with detected text regions would collapse this toward A, but the share of such images in a consumer library is [unknown].
- Scenario C (adds on-device LLM caption per image): on-device model tokens/s and image-prefill latency are [unknown] (round 0); at an illustrative 1.5 s/image [estimated: assumption only] this adds 12.5 h — infeasible in one session; captioning must be selective or server-side.
Conclusion: the embedding+face index for 30k photos fits in a single user-initiated Continued Processing session of roughly 15 minutes (floor) to one hour (central, derated); full-library OCR is 2.5–4 hours; full-library LLM captioning on device is not a one-night job on published evidence.

### Q4. Indexing from locally cached previews of iCloud-optimized assets

- Apple: with Optimize Storage "All of your original, full-resolution photos and videos are stored in iCloud while device-size versions are kept on your device." [sourced: Apple support article quoted in https://developer.apple.com/forums/thread/31019, Jan 2016 thread; dated]; current page says "space-saving copies are stored on your device" [sourced: https://support.apple.com/en-us/105061, via search snippet in the first pass; page not read]. **Resolution is not published by Apple [unknown].**

- Fit: MobileCLIP inputs are 256×256 (S0/S1/S2) and 224×224 (B) [sourced: arXiv 2311.17049v2 Table 12]; the ArcFace Core ML port takes a 112×112 face crop [sourced: RuiSumida/ArcFace-R100-CoreML README]; Vision face detection and OCR operate on whatever resolution is supplied, and the secondary ms figures above are quoted at unspecified resolution. A 1536×2048 local copy is ~6× the linear size of the CLIP input and leaves a 112-px face crop for any face wider than ~7% of the frame [estimated: 112 / 1536]; so the optimized copy is sufficient for embedding and for faces of ordinary size, and marginal only for very small faces or small text [estimated: from the input sizes above; no accuracy-vs-resolution test run]. The Foundation Models image path scales images itself ("performs the necessary scaling") [sourced: analyzing-images JSON].
- **Verdict: indexing needs no download for assets that have a local optimized copy; the fraction of a library with no local copy at all is [unknown] (Apple evicts by storage pressure; no rule published).** Treat `PHImageResultIsInCloudKey == true` as "skip, retry later on Wi-Fi".

### Q9. Exit path: importing face names

- **Apple Photos: no.** osxphotos `import` docs: "Photos will not import person names from the metadata" and "osxphotos cannot set person names in Photos (this is a limitation of Photos)."; workaround: "use the '{person}' template to add the names of the persons to the keywords"; `--sidecar` imports "title, description, keywords, location" [sourced: https://rhettbull.github.io/osxphotos/cli.html, import section, v0.77.x]. - **Google Photos: no documentation found [unknown].** Google's own pages: the Takeout help page says only that "Any additional metadata that isn't from the original file, like comments within Google Photos" goes to a separate JSON and "The photo or video metadata still has the original timestamp preserved in the metadata embedded within the files"; it does not mention people or face tags [sourced: https://support.google.com/accounts/answer/3024190, read 2026-11-03]. The Photos Library API upload guide documents only a `description` ("restricted to 1000 characters") and `fileName`; it says nothing about EXIF/XMP, sidecars or people metadata [sourced: https://developers.google.com/photos/library/guides/upload-media, read 2026-11-03]. The Google Photos "Edit your photos" help page (6128850) likewise says nothing about upload-time metadata [sourced: https://support.google.com/photos/answer/6128850, read 2026-11-03]. Secondary: Takeout JSON "contains structured metadata related to a specific photo, including the names of recognized faces" but "does not contain information about the identified faces location on the photo" — "only the names of the people" [sourced: https://tonfotos.com/articles/google-takeout/, updated 2024-09-27; secondary]. No Google page describing import of XMP people/regions was found.
- **Desktop tools: yes.** digiKam "will also create 'MWG regions'" when saving face tags, writes both MWG and Microsoft regions, reads Microsoft tags; "Some of the metadata, in particular that related to face recognition, is not stored in the images or .xmp sidecar files, but only in the digiKam database." [sourced: https://userbase.kde.org/Digikam/Tutorials/Setup_of_digiKam_for_Windows_compatibility]. Lightroom requires the MWG `AppliedToDimensions` tag: KDE bug 429219 ("MWG 'Applied To' state (mwg-rs:AppliedToDimensions XMP tag) is not included when writing Face metadata to file", reported 2020-11-17, RESOLVED FIXED 2021-11-15): "this issue also prevents the correct import of face tags into Lightroom."; "Because Lightroom considers mwg-rs without dimensions information invalid."; fix "add write mwg-rs:AppliedToDimensions XMP tag structure"; "digiKam itself still ignores AppliedToDimensions when importing." [sourced: https://bugs.kde.org/show_bug.cgi?id=429219, read 2026-11-03]. PhotoPrism (issue #5712) and Immich (discussion #4348) have open requests to read MWG regions [sourced: GitHub via search in the first pass; not re-read].
- Verdict: "you can leave with your names" holds as **XMP `PersonInImage` + MWG regions (with `AppliedToDimensions`) + dc:subject keywords** readable by digiKam/Lightroom/exiftool and importable to Apple Photos as *keywords*, but neither Apple Photos nor Google Photos will rebuild People albums from it. The honest claim is "portable names, not portable People albums".
